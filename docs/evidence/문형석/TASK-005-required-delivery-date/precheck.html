사전 검토: 필요 납기일 기입 기능 추가

작성: 문형석 (AI 초안, 사람 확인 전) · 2026-10-22 · 브랜치 feat/required-delivery-date · 결과는 report.html

1요청과 이해

요청고객이 '필요 납기일'을 요청할 수 있게 한다. 체크박스를 체크하면 '가능한 빨리', 원하는 납기일이 있으면 5~50일 중에서 고른다. 주문할 때 납기일을 넘는 경로는 빨간색으로 표시한다.
목적고객이 납기를 맞출 수 없는 경로를 확정하기 전에 알아보게 한다.
정하지 않은 부분과 가정① '가능한 빨리' = 납기 제한 없음(값 없음)으로 본다. ② 납기를 넘는 경로도 확정은 허용하고 표시만 한다("빨간색으로 표시"). ③ 납기일은 주문에 저장하고 상세에도 보여 준다. 사용자가 따로 답하지 않아 이 가정으로 진행했고, 바꾸고 싶으면 알려 달라고 했다.

2검토 영역과 근거

Yellow 주문 확정 흐름(서비스 검증, 저장, DB 컬럼 추가)과 주문 화면·상세 화면을 함께 건드리고, 화면 쪽 로직이 JS로 흩어져 있다.

  • 인증·결제·권한처럼 민감한 영역은 건드리지 않아 Red는 아니다.
  • 하지만 확정·저장 규칙과 DB 스키마(컬럼 추가)가 바뀌고, 기존 주문과의 호환(납기일 없음 = 가능한 빨리)을 확인해야 해서 Green도 아니다.
  • 그래서 Evidence를 꼼꼼히 보고, Diff 요약 리뷰와 테스트 보강 제안을 받는 Yellow로 둔다.

3위험 점검

위험점검 / 대응
기존 API 호환: 확정 요청에 requiredDays가 없어도 동작해야 한다값이 없으면 '가능한 빨리'로 처리. 기존 E2E 헬퍼(createOrderViaApi)와 기존 JUnit이 그대로 통과해야 한다(→ 검증 AC-6).
DB 컬럼 추가nullable 컬럼이라 ddl-auto=update로 안전하게 추가되고 기존 행은 '가능한 빨리'가 된다. 기존 DB 파일로의 기동은 직접 확인하지 못함(report 5장).
잘못된 입력(범위 밖, 빈 값, 소수)서버가 5~50을 검증하고 화면도 확정 전에 막는다(→ DLN-06, 서버 JUnit).
화면 표시와 서버 계산의 불일치주문 추가 화면은 시뮬레이션 소요 일수와 비교하고, 상세는 서버가 저장된 소요 일수와 비교한다. 같은 경로를 확정하면 같은 결과가 나오는지 DLN-04가 확인한다.
기존 테스트 약화기존 테스트를 고치지 않고 새 테스트만 추가한다.

4통과 기준 (핵심 체크리스트)

  1. AC-2 기본은 '가능한 빨리', 빨간 경로 없음
  2. AC-3 소요 일수가 납기일보다 긴 경로만 빨간색, 값을 바꾸면 바로 갱신
  3. AC-4 납기를 넘는 경로도 확정되고 상세에 정확히 표시
  4. AC-5 5~50 밖의 값은 화면과 서버 모두 거부
  5. AC-6 기존 JUnit·E2E 전부 통과, 새 E2E 반복에서도 안정
  6. AC-1·7·8 컴파일, 기존 테스트 변경 없음, 결과 파일에 개인 정보 없음
