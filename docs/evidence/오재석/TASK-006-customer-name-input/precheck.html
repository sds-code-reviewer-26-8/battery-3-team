1목표와 범위

만들 기능주문 확정 때 고객사 이름(선택)을 입력해 주문과 함께 저장하고, 확정·진행 상태에서는 이후에도 고쳐 쓸 수 있으며, 목록·상세에서 볼 수 있다.
선택한 이유주문을 고객사별로 구분해야 한다는 요구. 도전 요소는 (1) 자유 입력 문자열을 JS 로 그리는 화면의 이스케이프, (2) 기존 주문 행에 컬럼이 추가되는 영향, (3) 상태별 수정 허용과 낙관적 잠금.
영역 제안Yellow. 근거: 인증·결제·권한이 아닌 일반 업무 기능이라 Red 는 아니다. 다만 (1) 사용자 자유 입력을 innerHTML 로 그리는 화면(orders.js, order-detail.js)이라 XSS 를 직접 검증해야 하고, (2) 기존 E2E 중 목록 헤더를 고정 검증하는 테스트(lst.spec.ts:74)가 있어 기존 테스트를 그대로 믿기 어렵고, (3) 기준선 E2E 에서 MST-09 가 전체 실행 때 실패하는 불안정성이 확인됐다. 최종 결정은 사람.
이번에 포함 1) Order 엔티티에 nullable 컬럼 customerName(길이 100) 추가, 확정 요청(POST /api/orders)에 customerName 추가
2) 값 정규화: 앞뒤 공백 제거, 공백만이면 null, 100자 초과는 400(BusinessException)
3) 수정 API: PUT /api/orders/{id}/customer, 본문 {customerName, version}. 확정·진행만 허용, 완료는 400(이유 메시지), 취소(삭제)·없는 주문은 404, version 불일치는 409. 수정 성공 시 주문 version 증가, 응답은 갱신된 주문 상세
4) 목록·상세 응답에 customerName 포함
5) 화면: order-new 에 입력칸, order-detail 에 표시와 수정 폼(수정 가능한 상태일 때만), orders 목록에 '고객사' 열(없으면 '-')
6) JUnit 과 Playwright E2E 추가, 목록 헤더를 검증하는 기존 E2E 갱신
이번에 포함하지 않음수정 이력 저장, 고객사 마스터·자동완성·검색·필터, 기존 주문 데이터 이전, 확정 이후 다른 필드 수정, 미션 4 관련 작업, 작업 폴더의 무관한 변경(.gitignore, docs/e2e/, e2e/tests/login.spec.ts, e2e/tsconfig.json, e2e/results/, PROGRESS.md), 커밋·push·PR

  • 사람 확인이 좋은 점: (1) 목록의 고객사 열 위치(권장: 맨 끝, 기존 테스트 영향 최소) (2) 완료 상태 400 메시지 문구 (3) 수정 API 가 갱신된 상세를 돌려주는 방식(권장) (4) 영역(Yellow) 최종 결정.
  • 8080 서버는 IDEA 로 실행해 두었다. 구현 후 재시작해 기존 DB 호환(AC-12)을 확인한다.
