1목표와 범위

만들 기능서버가 화면(HTML)을 만들어 주는 Thymeleaf를 제거하고, 정적 HTML과 순수 JavaScript가 JSON API를 호출해 화면을 그리게 한다. 컨트롤러는 Model에 담아 템플릿 이름을 돌려주는 대신 JSON(DTO)을 돌려준다. (예: GET /orders/{id} → GET /api/orders/{id}가 OrderDetail을 JSON으로 반환)
선택한 이유팀장 지침(리팩토링 2). 이렇게 바꿔 두면 이후 React.js 프런트엔드 도입이 쉬워진다. 리팩토링 1(PR #18)은 병합되어 선행 조건 충족.
기능 분류Q1 저장 데이터 변경: 아니오 · Q2 되돌리기 어려운 동작: 아니오(코드만 변경, git으로 되돌림 가능) · Q3 기대 동작이 PRD에 정해져 있지 않음: 예(새 API 계약, 오류·메시지 표시 방식, 없는 주문 화면 등 PRD에 없음) · Q4 세 곳 이상 영향: 예(화면 5개, 컨트롤러, 인터셉터, 테스트) · Q5 금액·권한·보안: 예(로그인, 억 원 변환). 예 3개 + Q3 → L3. 사람이 기대 동작과 대안을 정한다.
이번에 포함 ① Thymeleaf 의존성·템플릿(templates/*.html)·spring.thymeleaf.* 설정 제거
② 화면 5개(login, orders, order-detail, order-new, master)를 정적 HTML + JS로 대체. 화면 URL은 그대로 유지(사용자 결정)
③ 화면이 쓰는 데이터를 JSON API로 제공: 주문 목록, 주문 상세, 상태 변경, 마스터 저장, 로그인 사용자 확인 등(8장의 제안 참고)
④ 공통 머리글(fragments)을 JS로 대체, 로그인 사용자 표시
⑤ 새 API를 검증하는 테스트 추가, 옛 계약에 묶여 있는 기존 테스트 일부 수정(사람 승인 필요, 4장)
⑥ 문서 갱신: CLAUDE.md(구조, 규칙), docs/INTENT.md 부록, 필요 시 docs/PRD.md
이번에 포함하지 않음React.js 도입, 업무 규칙·계산 로직 변경, DB 구조 변경, 화면 디자인(CSS) 변경, 기존 API(/api/master, /api/simulate, POST /api/orders)의 응답 형태 변경, 로그인을 세션 방식에서 토큰 방식으로 바꾸는 것, push·PR(사람이 요청할 때)

POST /login(폼, 성공 시 302 /orders, 실패 시 200 + 오류 문구), POST /logout, POST /orders/{id}/status(폼, 302 /orders/{id} + flash 메시지), POST /master(폼, 성공 302 /master, 실패 200 + 오류 목록)가 폼 전송 방식. JSON API는 GET /api/master, POST /api/simulate, POST /api/orders 3개뿐.

4영향 범위와 위험

영향받는 곳어떻게 영향받는가위험대응 / 확인 방법
templates/*.html 6개, build.gradle.kts, application.properties삭제(templates, thymeleaf 의존성 2개, thymeleaf 설정). 정적 HTML이 대체.중 화면 DOM이 달라지면 E2E가 깨짐기존 DOM 구조(class, id, name, 문구, 컬럼 순서)를 그대로 재현한다. 기존 E2E 수정 없이 통과하는 것을 기본 목표로 한다.
controller/* (Auth, Order, Master, Api, LoginUserAdvice)뷰 반환 메서드를 JSON API로 교체. 화면 URL(/orders 등)은 정적 HTML을 내주는 방식으로 유지(예: 포워드). LoginUserAdvice는 뷰 모델이 없어져 불필요.중 화면 URL 유지와 로그인 보호가 함께 동작해야 함JUnit pagesRender, E2E AUTH-01·05·06
config/LoginInterceptor, WebConfig정적 페이지 경로를 보호/제외하는 규칙 정리. 포워드된 내부 경로가 다시 로그인으로 보내지는 루프를 막아야 함.중 비로그인 접근 차단(FR-20, 원칙 8)이 약해지거나 무한 이동E2E AUTH-01·04·05·07·08·09, 직접 URL 접근 시나리오를 precheck AC에 포함
static/js 4개 + 새 JS머리글·목록·상세·마스터·로그인을 그리는 JS 추가. 상세 화면의 "계획 JSON을 스크립트에 주입"하던 방식이 API 응답으로 바뀜.중 서버 렌더링과 달리 그린 뒤 단언(E2E)하므로 타이밍 차이Playwright는 자동 대기. 화면에 보이는 로딩 중 상태가 단언과 충돌하지 않게 함.
INTENT 원칙 3·4·5·6 (서버 규칙)마스터 저장 경로, 상태 변경 경로가 새 JSON API로 옮겨감.중 옮기다 변경 번호 증가, 동시 수정 확인, 전부-아니면-전무 저장이 빠짐서비스(MasterService, OrderService)는 그대로 두고 컨트롤러만 교체. 단위·통합 테스트로 확인.
기존 JUnit 테스트 수정 필요 후보 (사람 승인 필요)
OrderFlowTests		wrongPasswordIsRejected: 로그인 실패를 200으로 단언 → 실패 응답 형식이 바뀌면 수정. masterUpdateBumpsVersionAndKeepsConfirmedPlans, invalidMasterIsNotSaved: POST /master 폼과 redirectedUrl("/master") 단언 → 마스터 저장 API가 바뀌면 수정.중게이트 ①에서 수정 범위를 사람이 승인. 검증 내용(버전 증가, 저장 안 됨)은 유지하고 호출 방식만 바꿈.
기존 E2E 수정 필요 후보 (사람 승인 필요)
hg.helpers.ts, mst.spec.ts, order-detail.spec.ts		 ① hg.helpers.ts countOrders: GET /orders의 HTML에서 class="clickable"을 세므로 정적 HTML이 되면 항상 0 → API 호출로 변경 필요 (8곳에서 사용).
② hg.helpers.ts restoreMaster: POST /master 폼 → 저장 API가 바뀌면 호출 변경 (3곳).
③ mst.spec.ts MST 동시 저장: pathname === '/master' && method === 'POST' 응답을 기다림 → 저장 API 경로로 변경.
④ order-detail.spec.ts DTL-05(취소 직후 500 알려진 결함), DTL-08(없는 주문 500 알려진 결함): test.fail(true)로 "실패하는 것이 정상"이라고 표시되어 있음. 새 구조에서 이 결함이 사라지면 "실패 표시했는데 통과"로 테스트가 실패한다. 테스트 주석이 "고쳐지면 test.fail 줄을 지운다"고 안내하므로 그 줄 제거가 필요. 단 취소 직후 이동 방식에 따라 DTL-05의 단언 방식(응답을 기다림)도 달라질 수 있음.		 중 E2E를 "하나도 안 고치고 통과"하는 것이 불가능한 지점이 있음게이트 ①에서 위 변경만 승인받고, 그 외 기존 E2E는 수정하지 않는다. 수정한 테스트는 report에 별도 표로 남기고 검증 내용이 약해지지 않았는지 적는다.
e2e 로그인 도우미 4곳(api.post('/login', {form}))폼 전송(application/x-www-form-urlencoded)으로 로그인하고 ok를 확인. 이 계약을 유지하면 수정 불필요.낮폼 로그인 엔드포인트 유지(7장 대안)
docs/*, CLAUDE.md구조 설명, "Thymeleaf 서버 렌더링" 기술 스택, 주의사항(전역 ExceptionHandler 없음, 취소 직후 redirect 등), 문서 속 화면·URL 설명이 달라짐.낮같은 변경에 갱신. 기대 동작을 바꾸는 부분은 사람 승인.
docs/understand/*, docs/loops/*, docs/evidence/우주상/TASK-001이전 작업의 설명·증거 문서에 옛 구조 설명이 남음.낮과거 증거이므로 수정하지 않음. 후속 정리 후보로만 기록.

되돌릴 수 없는 작업이 포함되는가? 없음. 코드·문서만 바뀌고 DB 구조와 데이터는 건드리지 않는다. 개발 DB(./data/battery)는 지우지 않고, E2E는 인메모리 DB(별도 포트)로 실행한다. 되돌리는 방법: 병합 전이면 브랜치 폐기, 병합 후면 병합 커밋 revert(Thymeleaf 의존성·템플릿이 함께 복구됨).

8사람이 정할 기대 동작 (제안)

아래는 AI의 제안이며 확정이 아닙니다. 게이트 ①에서 사람이 승인하거나 고칩니다. PRD에 정해진 내용이 없는 부분입니다(Q3).
#항목제안
1화면 URL유지(사용자 결정). 서버가 각 URL에 정적 HTML을 내준다. 정적 파일은 static/ 아래에 두고, 보호 규칙은 인터셉터가 맡는다.
2새 JSON APIGET /api/me(로그인 사용자) · GET /api/orders?status=(목록, 상태별 건수, 전체 건수) · GET /api/orders/{id}(주문, 상태 전이 후보, 버전, 이력, 저장된 계획) · POST /api/orders/{id}/status(상태 변경, 본문: status, version) · PUT /api/master(마스터 저장) · 로그아웃은 폼 POST /logout 유지 검토. 기존 3개 API는 그대로.
3오류 응답기존 형식 {error, conflict} 유지. 마스터 저장 검증 오류는 {errors:[…]}(여러 건 한꺼번에, FR-18). 상태: 입력 오류 400, 로그인 필요 401, 없는 주문 404, 충돌 409.
4없는 주문을 열면화면 URL은 정적 페이지(200)를 내주고, 화면이 "주문을 찾을 수 없습니다" 안내를 보여 준다. API는 404. (HTTP 500 결함 해소. PRD Q2의 "취소하면 삭제" 정책 자체는 바꾸지 않음.)
5상태 변경 후같은 화면에서 새 상태·이력을 다시 불러 보여 주고 성공 메시지(상태를 '진행'(으)로 바꿨습니다)를 띄운다. 취소는 주문이 삭제되므로 주문 목록으로 이동하고 목록에서 취소 안내를 띄울지 사람이 결정.
6마스터 저장 후같은 화면에서 성공 메시지를 띄우고 값을 다시 불러온다. 오류 시 입력값은 그대로 두고 오류 목록을 보여 준다(FR-18).
7로그인폼 전송 계약 유지(성공 시 302 /orders). 실패 시 JS가 같은 화면에서 오류 문구를 보여 주고 URL은 /login에 머문다. 실패 응답의 HTTP 상태(현재 200)를 401로 바꿀지 사람이 결정(바꾸면 기존 JUnit 1개 수정).
8억 원 변환 위치저장 값은 원 단위 그대로. 화면에서 억 원으로 입력·표시하는 변환은 현재 서버(MasterController가 나눔, MasterService가 곱함)에 있다. 새 구조에서도 변환 책임을 서버에 두고 API는 억 원 문자열을 주고받는 안을 제안(규칙 변경 없음).
