3반복 횟수

한 줄 요약: Thymeleaf와 템플릿을 제거하고 화면 5개를 정적 HTML + JS로, 서버 컨트롤러를 JSON API로 바꿨다(화면 URL 유지). JUnit 33/33(기존 22 + 신규 11), E2E 78 통과(기존 72 + 신규 6), 건너뜀 1개는 깨끗한 DB에서 따로 통과. 승인받은 기존 테스트 수정 외의 기존 테스트는 고치지 않았다. 승인한 안과 다른 점 1가지(취소 후 동작, 2장)가 있다.

※ 위 숫자는 3장 표(id="results")의 행만 센다. 표 밖의 건너뜀·미확인은 집계되지 않으므로 5장을 함께 읽는다. "건너뜀·미확인 0"을 "문제 없음"으로 읽지 않는다.

2구현 요약

구현한 것사용자에게 보이는 화면과 주소는 같다. 서버가 HTML을 만들어 주던 방식을, 정적 HTML이 열린 뒤 JS가 JSON API로 데이터를 받아 그리는 방식으로 바꿨다. 오류 응답이 모두 JSON({error, conflict}, 여러 건이면 errors)이 되었고, 없는 주문은 HTTP 500 대신 404(화면은 안내 문구)다.
접근 방법① 화면 주소(/orders, /orders/new, /orders/{id}, /master, /login)는 PageController/AuthController가 정적 HTML로 포워드한다. ② 데이터는 /api/me, /api/orders(목록·상세·확정·상태 변경), /api/master(조회·/form·저장 PUT), /api/simulate가 준다. ③ 업무 오류는 ApiExceptionHandler가 모아서 변환한다. ④ 서비스(MasterService, SimulationService, OrderService)의 업무 규칙은 바꾸지 않았다(찾을 수 없음을 구분하는 오류 종류 추가만, 3장 AC-10). ⑤ 화면 스크립트는 최상위 await로 데이터를 받아 그린다. 처음에는 이것이 "그린 뒤에야 페이지 로딩이 끝나게 해서 로드 직후 읽는 기존 E2E가 그대로 동작한다"고 보았지만, PR 리뷰의 반복 실행에서 보장되지 않음이 확인되었다(4장 3회차). 그래서 로드 직후 읽는 테스트 쪽에 명시적 대기를 추가했다.
승인한 안과 다른 점취소 후 동작: precheck 8장 5번은 "취소 후 주문 목록으로 이동"이었다. 구현해 보니 취소 직후 이동이 비동기라서, 취소 바로 뒤에 goto('/orders')를 하는 기존 E2E(DTL-06)가 이동과 겹쳐 실패했다(폼 전송 방식에서는 클릭이 이동 완료까지 기다려 줬던 차이). 그래서 같은 화면에 "주문 #N을(를) 취소했습니다" 안내와 "목록으로" 버튼을 보여 주는 방식으로 바꿨다. 사람이 승인한 동작과 다르므로 게이트 ②에서 확인이 필요하다.

    원인: 구현 설명의 오류 + 검증 방법의 취약함. 최상위 await가 페이지 로딩 완료를 보장한다는 가정이 틀렸고, 로드 직후 바로 읽는 테스트(chipCounts, LST-04, LST-06)가 화면이 그려지기를 기다리지 않았다.

    재검증: E2E 전체 3회 반복 실행(results/after-e2e-repeat3.json), 단일 실행, JUnit, 컴파일 (수치는 3장·1장).
  2. 1회차 — 실패 후 수정, 재검증 통과
    실패 내용: E2E 1건 실패. DTL-06 "취소된 주문은 목록에서 사라지고…" — page.goto: net::ERR_ABORTED at /orders
    원인: 구현(설계)의 문제. 취소 성공 뒤 JS가 비동기로 /orders로 이동시키는데, 테스트는 취소 클릭 직후 바로 goto('/orders')를 해서 두 이동이 겹쳐 하나가 중단됨. 폼 전송 방식에서는 클릭이 이동이 끝나길 기다려 줬기 때문에 드러나지 않던 차이.
    조치: 취소 후 이동하지 않고 같은 화면에 취소 안내를 보여 주도록 구현 변경(승인한 안과 달라짐, 2장). 이에 맞춰 DTL-05가 기다리는 응답을 변경(승인된 테스트 수정 범위 안). → 재검증 결과: 통과 (E2E 72 + 신규 5)
  3. 2회차 — 실패 후 수정, 재검증 통과
    실패 내용: 새 JUnit 1건 실패. pageUrlsServeStaticHtmlAndStayProtected — 로그인 화면 HTML 안의 한글을 문자열로 비교했으나 MockMvc가 정적 파일을 ISO-8859-1로 읽어 한글이 깨짐.
    원인: 검증 방법 오류(앱은 맞고 테스트의 단언 방식이 틀림). 새로 추가한 테스트이므로 사람 승인 대상이 아님.
    조치: 한글 대신 ASCII 요소 id="loginForm"으로 단언 → 재검증 통과(당시 JUnit 31/31).

5건너뛴 것과 확인하지 못한 것

  • 전체 E2E에서 LST-04 1개 건너뜀 — 주문이 이미 쌓인 환경에서는 재현할 수 없는 조건부 테스트. AC-9에서 깨끗한 DB로 따로 실행해 통과를 확인했다. 3장 표에는 AC-9가 "통과"로 들어 있으므로 전체 실행에서 건너뛴 사실은 여기에만 있다.
  • 최상위 await는 "로딩 완료 전에 그려지는 것"을 보장하지 않는다(3회차에서 확인). 이 PR은 이를 믿지 않고 테스트에 명시적 대기를 추가했다. 이 방식 자체는 Chromium에서만 확인했고 Firefox·Safari는 미확인이다. 최상위 await는 최신 브라우저에서만 동작한다(지원 브라우저 범위는 정해져 있지 않음).
  • 요청 형식 오류의 JSON 응답은 이번에 추가했지만, 로그인 인터셉터의 401은 Spring 기본 형식({timestamp, status, error, path})이다. 개발 환경에서는 spring-boot-devtools 때문에 기본 오류 응답에 스택 트레이스(trace)가 포함될 수 있다(이 PR이 만든 문제가 아니고 개발 환경 한정, 운영 설정은 미확인).
  • 취소한 주문 화면을 새로고침하면 주문이 이미 삭제되어 "주문을 찾을 수 없습니다"로 바뀐다. 화면의 안내 문구("삭제되어 목록에서 사라집니다")는 PRD 열린 질문 Q2(취소 시 삭제) 정책을 그대로 알린다. 정책이 바뀌면 이 문구와 동작도 바뀌어야 한다.
  • JS 없이는 로그인·마스터 저장이 동작하지 않는다(폼이 JS로 가로채어 API로 전송). 마스터 폼의 action="/master" 속성은 기존 E2E 도우미가 이 선택자로 폼을 찾기 때문에 남겼고, 서버에 POST /master는 더 이상 없다.
  • 화면을 사람이 직접 눈으로 보는 수동 확인은 하지 않았다(E2E가 문구·컬럼·동작을 단언). L3 필수 범위인 "수동 확인"을 실행하지 못했다 → 게이트 ②에서 사람이 화면을 한 번 열어 보길 권한다(./gradlew bootRun 후 /login).
  • 비숫자 주문 번호(/orders/abc)는 이제 화면 연결에 걸리지 않고 404다(리뷰 중 실행으로 확인). 변경 전에는 400이었다.
  • 동시 요청 부하와 트랜잭션 차이는 별도로 확인하지 않았다(precheck 그대로).
  • 이 문서는 승인 칸을 비워 두었다. 사람 확인 전이다. 사전 검토 때 사람이 대화에서 답한 결정은 precheck에 기록했다.
