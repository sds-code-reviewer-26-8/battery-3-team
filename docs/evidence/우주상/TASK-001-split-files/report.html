2구현 요약

구현한 것사용자에게 보이는 변화는 없다(URL, 화면, JSON 응답 동일). 코드 구조만 바뀌었다.
접근 방법메서드 본문은 그대로 옮기고 호출 대상·클래스 이름만 바꿨다. 확정(OrderService)이 시뮬레이션(SimulationService)을, 시뮬레이션이 마스터 조회(MasterService)를 호출하는 한 방향 의존이다. 로그인 아이디 공통 모델은 @ControllerAdvice로 옮겼다. 적용 범위는 넓어졌다: 전에는 AppController 안에서만 적용되던 것이 이제 모든 컨트롤러(Spring 기본 오류 컨트롤러 /error 포함)에 적용된다. 템플릿이 loginUser를 읽는 방식은 같아 영향은 작아 보이나(코드 읽기 기반, 별도 확인 안 함), 이름은 같고 범위만 다르다.
리뷰 반영: 같은 타입 주입의 필드명을 통일했다(서비스는 xxxService, 저장소는 xxxRepository).

5건너뛴 것과 확인하지 못한 것

  • 전체 E2E에서 LST-04 1개 건너뜀 — 주문이 이미 쌓인 환경에서는 재현할 수 없는 조건부 테스트. AC-3에서 깨끗한 DB로 따로 실행해 통과를 확인했다. 3장 표에는 AC-2가 "통과"로 들어 있으므로, 전체 실행에서 건너뛴 사실은 여기에만 있다.
  • 린트 미설정: 컴파일 에러 0만 확인했고 경고 수는 집계하지 않았다. E2E TypeScript 타입 검사는 미확인(변경 없음).
  • 화면을 직접 눈으로 확인하는 수동 점검은 하지 않았다(L2 필수 범위 아님, E2E가 화면 문구·컬럼을 단언함).
  • /api/simulate 경로의 트랜잭션 변화: simulate()를 단독으로 호출하는 경로는 전에는 같은 클래스 안 호출이라 읽기 전용 트랜잭션 없이 실행됐다. 지금은 MasterService 프록시를 거쳐 읽기 전용 트랜잭션으로 실행된다. 공장·항로·설정을 한 트랜잭션에서 읽게 되어 문제는 없어 보이나 코드 읽기 기반 추정이고, 별도로 실험하지는 않았다(JUnit·E2E는 통과).
  • 동시 요청 시 트랜잭션 동작 차이는 별도 부하 테스트로 확인하지 않았다. 확정은 OrderService 한 트랜잭션 안에서 시뮬레이션을 호출하는 구조이며, 낙관적 락은 OrderFlowTests가 확인한다.
  • 이 문서는 승인 칸을 비워 두었다. 사람 확인 전이다. 사전 검토 때 사람이 대화에서 답한 결정(질문 1~3)은 precheck.html 8장에 기록했다.
