1목표와 범위

만들 기능동작을 바꾸지 않고, 한 파일에 몰려 있는 Controller·Service·Repository 코드를 역할별 파일로 나눈다.
선택한 이유AppController(198줄), BatteryService(303줄)에 여러 책임이 섞여 있고, Repository는 중첩 인터페이스 묶음이라 찾기 어렵다.
기능 분류Q1 저장 데이터 변경: 아니오 · Q2 되돌리기 어려운 동작: 아니오 · Q3 기대 동작 미정: 아니오(동작 유지가 기준) · Q4 세 곳 이상 영향: 예(화면·API·테스트·초기화) · Q5 금액·권한·보안: 예(운항비 환산, 로그인 처리가 이동 대상). 예 2개이고 Q2·Q3 아님 → L2. Q5가 걸려 있어 사람이 L3로 올릴 수 있다.
이번에 포함 Controller: AppController → AuthController(/, /login, /logout), OrderController(/orders…), MasterController(/master), ApiController(/api/*), 로그인 사용자 공통 모델은 별도 클래스(@ControllerAdvice)
Service: BatteryService → MasterService(초기값·조회·검증 저장), SimulationService(주문 검증·시뮬레이션), OrderService(확정·조회·상태 변경)
Repository: 중첩 인터페이스 5개(Setting, Factory, Route, Order, OrderStatusHistory)를 각각 최상위 파일로
위 변경으로 import가 바뀌는 곳(DataInitializer), 그리고 이름이 바뀌어 어긋나는 문서(CLAUDE.md, INTENT.md 부록)
이번에 포함하지 않음Planner·entity·config 로직 변경, URL·화면·JSON 응답 형태 변경, 업무 규칙 변경, 린트 도구 도입, push·PR

3현재 상태 확인

확인한 방법변경 전 상태(main에서 딴 브랜치, 코드 변경 없음)에서 .\gradlew.bat test --rerun-tasks 와 cd e2e; npx playwright test 실행
확인 결과JUnit 22개 통과(DemoApplicationTests 1, OrderFlowTests 9, PlannerTest 12), 실패 0. E2E 72개 통과, 1개 건너뜀, 실패 0(약 94초).

건너뛴 1개: e2e/tests/lst.spec.ts:65 — "주문이 이미 있어 빈 상태를 재현할 수 없음(깨끗한 DB에서만 실행)". 조건 때문에 건너뛴 것이므로 D3에서 격리된 환경에서 따로 실행해 보완한다. 증거: results/before-junit/ (JUnit XML).

4영향 범위와 위험

영향받는 곳어떻게 영향받는가위험대응 / 확인 방법
controller/AppController (외부 참조 0곳)4개 컨트롤러 + 공통 모델 클래스로 분리. SimulateRequest·ConfirmRequest 레코드는 ApiController로 이동.중 공통 모델 loginUser가 모든 화면에 적용되어야 함@ControllerAdvice로 옮겨 전 컨트롤러에 적용. E2E auth·lst·mst 시나리오로 상단 아이디 표시 확인.
service/BatteryService (참조: AppController, DataInitializer, OrderFlowTests)3개 서비스로 분리. confirm이 simulate를 호출하므로 OrderService → SimulationService → MasterService 순으로 의존.중 같은 클래스 안 호출이 빈 사이에 프록시를 거치게 됨(트랜잭션 경계 변화)confirm은 쓰기 트랜잭션 하나 안에서 실행되고 안쪽 호출은 거기에 합류하므로 확정·저장은 한 트랜잭션으로 유지됨. OrderFlowTests(확정·상태 변경·낙관적 락)로 검증.
INTENT 원칙 1·3·4·5해당 코드를 그대로 옮기고 로직은 바꾸지 않음.중 이동 중 검증·masterVersion 증가·재계산 단계 누락이동 전후 diff 검토, OrderFlowTests·E2E(order-confirm, mst, api)로 확인.
repository/*Repositories (참조: BatteryService import 5줄)중첩 인터페이스 → 최상위 인터페이스 5개. 패키지가 같아 JpaConfig 스캔 범위 변화 없음.낮 스프링 데이터 등록 누락DemoApplicationTests(컨텍스트 로딩), 전체 테스트.
config/DataInitializerinitDefaults 호출 대상이 MasterService로 바뀜(1줄+import). 범위 밖 파일이지만 컴파일에 필수.낮게이트 ①에서 범위 포함 승인 요청.
src/test/.../OrderFlowTestsBatteryService를 주입해 getOrder·changeStatus·history를 호출 → 서비스 분리 시 컴파일 불가. 기존 테스트 수정이 필요한 지점.중게이트 ①에서 방식 결정(8장 질문 1).
e2e/testsURL·화면·JSON 응답이 그대로라 영향 없음. 주석 2곳(hg.helpers.ts:14, sim.spec.ts:20)이 BatteryService.initDefaults를 언급(주석만).낮E2E 72개 그대로 실행. 주석은 수정하지 않음(기존 테스트 파일).
CLAUDE.md, docs/INTENT.md 부록클래스 이름이 바뀌어 안내가 어긋남.낮같은 변경에 갱신. 설계 의도 자체는 바꾸지 않으므로 기대 동작 변경 아님.

되돌릴 수 없는 작업이 포함되는가? 없음. 파일 삭제는 git으로 복원 가능하고, push·PR·DB 삭제는 하지 않는다. E2E는 인메모리 DB(포트 18080)에서 실행하므로 개발 DB(./data/battery)는 건드리지 않는다.

5환경·세팅 점검

  • 앱을 실행할 수 있다
    확인 근거: E2E가 gradlew bootRun으로 18080 포트에 서버를 띄워 72개 통과
  • 기존 테스트가 통과한다 (기준선)
    확인 근거: JUnit 22/22 통과, E2E 72 통과·1 건너뜀·0 실패
  • 작업 브랜치를 만들었다
    확인 근거: refactor/split-large-files (main 0285f62에서 분기)
  • 테스트 데이터·DB 상태를 알고 있다
    확인 근거: JUnit은 메모리 H2(create-drop), E2E는 jdbc:h2:mem:battery-e2e. 개발 DB와 분리됨.
  • 필요한 도구·설정이 갖춰졌다
    확인 근거: Gradle wrapper 9.8.1, Playwright 설치됨(e2e/node_modules). 린트 도구는 설정되어 있지 않음 → 컴파일로 대체. 컴파일 기준선: 에러 0(테스트 실행 시 compileJava·compileTestJava 성공). E2E(TypeScript)는 타입 검사 도구가 없어 미확인이지만 이번엔 E2E 코드를 바꾸지 않음.

새 TC 추가: 이번 변경은 동작을 바꾸지 않는 리팩토링이라 새 기능 TC는 추가하지 않고, 기존 테스트로 동작 유지를 확인한다(회귀가 곧 검증). 사유는 report에 기록한다. 구현 이전 코드에서 TC가 실패하는지 보는 절차는 해당 없음.

8미확인 사항과 열린 질문

  • 질문 1 (결정 필요) OrderFlowTests가 BatteryService를 직접 주입한다. ⓐ 서비스를 분리하고 이 테스트의 주입·import만 새 서비스로 바꾼다(검증 내용은 그대로, 기존 테스트 수정 승인 필요, 추천) / ⓑ 테스트를 건드리지 않도록 BatteryService를 얇은 위임용 파사드로 남긴다(파일 분리 효과가 줄고 중간 계층이 늘어남).
  • 질문 2 (범위) DataInitializer(config) 1곳 수정을 범위에 넣어도 되는가. 컴파일에 필수.
  • 질문 3 (범위) CLAUDE.md(아직 커밋 전 파일)와 docs/INTENT.md 부록의 클래스 이름을 같은 변경에서 갱신해도 되는가. CLAUDE.md를 이번 커밋에 포함시킬지도 확인 필요.
  • JpaConfig의 considerNestedRepositories=true는 분리 후 불필요해지지만 그대로 둔다(동작 영향 없음, config 최소 변경). 정리하고 싶으면 알려 달라.
  • 린트: 도구 미설정, 컴파일로 대체(E2E TypeScript 타입 검사는 미확인, 이번엔 E2E 코드 변경 없음).
