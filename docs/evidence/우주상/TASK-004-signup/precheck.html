1목표와 범위

만들 기능기능 추가/변경 4 "사용자 추가": 회원 가입 후 로그인할 수 있다. 회원 가입으로 가입된 회원은 모두 admin과 같은 권한을 갖는다.
선택한 이유사람(담당자)이 맡은 기능. 현재는 admin/admin 계정 하나가 코드에 정해져 있어 다른 사람이 들어올 방법이 없다.
기능 분류Q1 저장 데이터 변경: 예(사용자 정보를 저장하는 새 테이블) · Q2 되돌리기 어려운 동작: 아니오(코드 변경, 새 테이블이 남을 뿐) · Q3 기대 동작이 PRD에 정해져 있지 않음: 예(가입 규칙, 가입 후 흐름, 비밀번호 저장 방식) · Q4 세 곳 이상 영향: 예(로그인, 화면, 인터셉터, 초기 데이터, 테스트, 문서) · Q5 금액·권한·보안: 예(계정과 비밀번호). 예 4개 + Q3 → L3. 사람이 기대 동작과 대안을 정한다.
이번에 포함 ① 가입 화면(/signup)과 가입 API, 로그인 화면의 "회원가입" 링크
② 사용자 저장(새 테이블), 비밀번호는 해시로 저장
③ 로그인을 저장된 사용자 기준으로 변경(admin/admin은 그대로 로그인 가능)
④ 가입한 회원이 admin과 같은 전체 기능을 쓸 수 있음(현재 역할 구분이 없으므로 별도 권한 코드는 필요 없고, 이를 테스트로 확인)
⑤ 테스트 추가(JUnit, E2E), 문서 갱신(PRD, INTENT, CLAUDE.md는 로컬)
⑥ 코드 정리 1건: 이전 작업(PR #21)의 주문 상세 화면 스크립트에 남은 반복 문자열을 상수로 정리(사람 결정: 문서 없이 코드 수정만, 별도 커밋)
이번에 포함하지 않음역할·권한 구분, 비밀번호 변경·찾기, 회원 탈퇴·수정·목록, 이메일 인증, 가입 횟수 제한(스팸 방지), 로그인 실패 횟수 제한, 자동 로그인(가입 직후 로그인 상태로 만들기), 서비스(주문·마스터·시뮬레이션)의 업무 규칙 변경, push·PR(사람이 요청할 때)

4영향 범위와 위험

영향받는 곳어떻게 영향받는가위험대응 / 확인 방법
새 파일: entity, repository, service, controller, 화면사용자 엔티티·저장소, 가입·인증 서비스, 가입 컨트롤러, signup.html·signup.js, 로그인 화면에 링크중 새 코드가 기존 규칙(원칙 5·6)과 어긋나지 않아야 함오류 응답 형식·검증 방식을 기존과 같게(전부 검증 후 저장, 이유를 한꺼번에 알림)
controller/AuthController 로그인하드코딩 비교 → 저장된 사용자와 비밀번호 해시 비교. admin/admin은 시작할 때 사용자 테이블에 넣어 계속 로그인 가능하게 한다.중 기존 E2E·JUnit이 모두 admin으로 로그인하므로 깨지면 파급이 큼기존 JUnit·E2E를 수정 없이 통과시키는 것을 기준으로 함(AC-8)
config/WebConfig, LoginInterceptor/signup, /signup.html, /api/signup을 로그인 없이 열어야 한다.중 제외 범위를 잘못 넓히면 비로그인 접근이 열림(원칙 8, FR-20)정확한 경로만 제외하고, 비로그인 접근 E2E(AUTH-01~09)로 확인
config/DataInitializer시작할 때 admin 사용자가 없으면 만든다(있으면 건드리지 않음).낮 기존 개발 DB 파일과 호환새 테이블만 자동 생성되고 기존 테이블은 그대로. 이미 admin이 있으면 중복 생성 안 함(테스트로 확인)
build.gradle.kts의존성 spring-security-crypto 한 줄 추가(해시용). Spring Security 설정은 쓰지 않는다.중 빌드 설정 변경(승인 필요)게이트 ①에서 승인. 대안은 7장.
보안(Q5)공개 가입이므로 누구나 가입해 admin과 같은 권한(기준 정보 수정 포함)을 얻는다. 요구사항이 정한 동작이며 PRD가 이미 지적한 "권한 없음" 한계를 넓힌다. 가입 횟수 제한·비밀번호 정책이 약하면 스팸·약한 비밀번호 위험.중 사람이 인지하고 수용해야 함report와 PRD에 한계로 기록. 비밀번호는 해시로 저장하고 로그인 실패 메시지는 기존과 같게(아이디·비밀번호 중 무엇이 틀렸는지 알리지 않음).
INTENT 원칙 8, 3장작성자·처리한 사람 기록이 가입한 아이디로 남아야 한다.낮가입 계정으로 주문 확정·상태 변경 후 기록 확인(AC-4)
기존 테스트로그인·인증 관련 E2E(AUTH-*), JUnit(OrderFlowTests, JsonApiTests)은 모두 admin/admin을 쓴다. 로그인 화면의 getByLabel('아이디')·getByLabel('비밀번호')를 쓰는데 링크 하나가 추가될 뿐이다.낮 기존 테스트 수정은 필요 없을 것으로 예상수정이 필요해지면 멈추고 사람에게 묻는다(범위 밖).
테스트 데이터E2E는 같은 인메모리 DB를 쓰며 반복 실행(--repeat-each)도 한다. 가입 테스트는 실행마다 겹치지 않는 아이디를 써야 한다.낮가입 테스트는 무작위 접미사가 붙은 아이디 사용, 개발 DB는 건드리지 않음
docs/PRD.md, docs/INTENT.md, CLAUDE.md"계정은 admin 하나", "계정 관리는 범위 밖", FR 목록, Q3 문구 등을 새 동작에 맞게 갱신낮기대 동작을 바꾸는 갱신이므로 게이트 ①에서 승인(CLAUDE.md는 로컬 파일, 커밋 제외)

되돌릴 수 없는 작업이 포함되는가? 없음. 새 테이블이 생기지만 지우지 않는다. 병합 후 되돌리려면 병합 커밋을 revert하면 되고, 남는 users 테이블을 지우는 것은 데이터 삭제라 사람이 승인한 뒤에 한다. push·PR은 사람이 요청할 때 한다. 개발 DB(./data/battery)는 지우지 않고, E2E는 인메모리 DB(별도 포트)에서 실행한다.

7대안 비교와 되돌리는 방법 (L3)

대안내용장점단점·위험
A. 사용자 테이블 + BCrypt 해시 (추천)새 users 테이블에 아이디·비밀번호 해시를 저장하고, 비밀번호 해시는 spring-security-crypto의 BCrypt로 한다. admin은 시작할 때 이 테이블에 넣는다.검증된 해시 구현을 쓴다. 가입자와 admin을 같은 방식으로 다룬다. 필요한 부분(해시)만 의존성으로 추가한다.빌드에 의존성이 한 줄 늘어난다.
B. 사용자 테이블 + JDK PBKDF2새 의존성 없이 JDK가 주는 PBKDF2로 해시를 직접 구현한다.의존성 변화가 없다.해시·소금값·비교 코드를 직접 만들고 검증해야 해서 실수 위험과 리뷰 부담이 크다.
C. 메모리·파일에 저장데이터베이스를 쓰지 않고 메모리나 파일에 저장한다.구현이 간단하다.다시 시작하면 가입이 사라지거나(메모리), 기존 방식과 어긋난다. 요구("가입 후 로그인 가능")를 안정적으로 만족하지 못한다. 평문 저장은 어떤 대안에서도 하지 않는다.

#항목제안
1가입 화면/signup(로그인 없이 열림). 입력: 아이디, 비밀번호, 비밀번호 확인. 로그인 화면에 "회원가입" 링크. 로그인한 사용자가 열면 주문 목록으로 이동(/login과 같음).
2아이디 규칙영문·숫자·밑줄(_) 4~20자. 대소문자 구분 없이 같은 아이디로 보고 소문자로 저장한다(예: Admin과 admin은 같음). 로그인할 때도 같은 방식으로 비교한다.
3비밀번호 규칙8~64자(공백 포함 가능, 앞뒤 공백은 그대로)이며 BCrypt 한계로 UTF-8 72바이트 이하(한글은 24자까지)여야 한다(PR 리뷰로 보완). 비밀번호와 확인이 같아야 한다. (기존 admin/admin은 이 규칙의 예외로 유지)
4검증과 오류틀린 값이 하나라도 있으면 가입하지 않고 이유를 한꺼번에 모아 보여 준다(기준 정보 저장과 같은 방식). 입력한 아이디는 남기고 비밀번호는 비운다. 중복 아이디는 409, "이미 사용 중인 아이디입니다".
5가입 후가입 완료 안내와 "로그인하러 가기" 링크를 보여 주고 자동 로그인하지 않는다(요구가 "가입 후 로그인이 가능"이라서).
6권한가입한 회원은 admin과 같은 전체 권한. 역할 구분 없음(현재와 같음). 주문 작성자·상태 변경 기록에는 가입한 아이디가 남는다.
7admin 계정그대로 admin/admin. 시작할 때 사용자 테이블에 없으면 만든다. 가입으로 admin 아이디를 쓸 수 없다.
8로그인 실패기존과 같은 문구와 401(아이디·비밀번호 중 무엇이 틀렸는지 알리지 않음).
