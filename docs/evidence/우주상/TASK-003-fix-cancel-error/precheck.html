1목표와 범위

만들 기능확정·진행 상태 주문에서 "취소(으)로 변경"을 눌러도 에러 페이지(HTTP 500)가 뜨지 않게 고친다. 없는 주문 번호의 화면(/orders/{id})도 서버 오류 대신 안내를 보여 준다.
선택한 이유슬라이드 13쪽 "버그 발생 - 주문 취소시 에러 페이지가 뜹니다". PRD "결함 후보"에도 올라 있다. 원인은 취소가 주문을 삭제한 뒤, 삭제된 주문의 상세 화면으로 이동해 주문을 다시 찾으려다 BusinessException이 처리되지 않고 500이 되는 것이다.
기능 분류Q1 저장 데이터 변경: 아니오 · Q2 되돌리기 어려운 동작: 아니오 · Q3 기대 동작이 PRD에 정해져 있지 않음: 예(취소 직후 화면과 취소 주문 조회 여부는 PRD 열린 질문 Q2가 미정) · Q4 세 곳 이상 영향: 예(화면 주소, 화면 JS, 오류 처리, 테스트, PRD) · Q5 금액·권한·보안: 아니오. Q3가 "예" → L3. 사람이 기대 동작과 대안을 정한다.
이번에 포함① 화면 주소 /orders/{id}와 취소 직후 동작 수정 ② "알려진 결함" 표시를 달아 둔 E2E(DTL-05, DTL-08)를 정상 통과하게 정리 ③ 수정한 동작을 확인하는 새 테스트 ④ PRD 결함 후보 문구 갱신
이번에 포함하지 않음취소한 주문을 삭제하지 않고 남기는 정책 변경(PRD Q2), 서비스의 업무 규칙(재계산, 버전 비교, 상태 전이), 화면 디자인, 다른 화면, push·PR(사람이 요청할 때)

7대안 비교와 되돌리는 방법 (L3)

대안내용장점단점·위험
A. 같은 화면에 취소 안내 (추천)취소 API가 이미 돌려주는 deleted:true를 받으면, 삭제된 주문을 다시 조회하지 않고 같은 화면에 "주문 #N을(를) 취소했습니다" 안내와 "목록으로" 버튼을 보여 준다. 없는 주문의 화면 주소는 화면(HTML)을 내주고 안내는 화면이 보여 준다(API는 404).취소 직후 다른 화면으로 이동하는 기존 E2E와 겹치지 않아 안정적이다. PR #19에서 구현·리뷰된 방식이다.취소한 화면을 새로고침하면 "주문을 찾을 수 없습니다"로 바뀐다(주문이 삭제되므로 정책상 자연스러움).
B. 취소 후 주문 목록으로 이동취소 후 /orders로 이동한다(안내 문구는 선택).화면 흐름이 단순하다.이동이 비동기라서 취소 직후 goto하는 DTL-06이 간헐 실패(리팩토링 2에서 겪음). 피하려면 동기 요청이 필요하거나 기존 E2E를 고쳐야 한다.
C. 취소한 주문을 삭제하지 않고 남김상태만 CANCELED로 두고 목록에서 걸러 보이거나 조회할 수 있게 한다.취소 후 주문을 조회할 수 있어 근본적이다.PRD Q2(취소하면 삭제가 의도인가)를 바꾸는 정책 변경이고 서비스·DB·목록 규칙이 바뀐다. 이번 범위 밖.

추천: A. 되돌리는 방법: 병합 전에는 브랜치 폐기, 병합 후에는 병합 커밋 revert(버그가 다시 나타남). DB·데이터 변경은 없다. 영향받는 문서: docs/PRD.md(결함 후보, Q2의 참조 문구), CLAUDE.md(로컬).

#항목제안
1취소 성공 후같은 화면에 "주문 #N을(를) 취소했습니다. 취소한 주문은 삭제되어 목록에서 사라집니다." 안내와 "목록으로" 버튼. 상태 변경 버튼은 없음. 주소는 그대로.
2없는 주문의 화면 주소HTTP 200으로 화면을 열고 "주문을 찾을 수 없습니다" 안내와 "목록으로" 버튼을 보여 준다. JSON API는 404 유지.
3취소 요청이 실패하면(충돌, 입력 오류)이유를 보여 주고 최신 상태를 다시 불러온다(다른 상태 변경과 같음).
4다른 화면 오류이번에는 건드리지 않는다.
