# INTENT: 배터리 운송 주문·경로 시뮬레이션

### 이 문서에서 쓰는 말

| 말 | 뜻 |
|---|---|
| **기준 정보** | 계산의 바탕이 되는 값. 공장별 생산 능력·보관 한도·셀 1개 원가, 나라 사이 뱃길 일수, 배의 수와 하루 운항비, 공장별 하루 운영비 |
| **계획안** | 어떤 배가 언제 출발해 어느 나라를 어떤 순서로 돌고, 총 며칠에 얼마가 드는지를 정리한 운송 계획 |
| **확정** | 마음에 드는 계획안을 골라 정식 주문으로 만드는 것 |

이 문서는 시스템이 **왜 이렇게 만들어졌는지**를 설명합니다. 무엇을 하는 시스템인지는 `PRD.md`에 있습니다.
"근거"는 시스템 안에 직접 적혀 있는 설명, 화면 문구, 실제 동작에서 확인한 것만 적었습니다(확인할 수 있는 위치는 맨 아래 부록). 근거를 찾을 수 없는 부분은 마지막 "의도를 확인할 수 없는 부분"에 모았습니다.

## 1. 한 줄 의도

**배터리 생산·수거 비용을 미리 계산해 비교하고, 확정한 주문은 나중에도 그때 그대로 확인할 수 있게 한다.**

- 근거: 로그인 화면의 소개 문구가 "배터리 생산 / 수거 비용 예측 및 주문 관리"입니다.

## 2. 설계 의도

각 항목은 "무엇을 지키려는가 → 그래서 어떻게 했는가" 순서입니다.

| # | 의도 | 그래서 이렇게 했다 | 근거 |
|---|---|---|---|
| 1 | **화면에 보인 숫자를 그대로 믿지 않는다** | 주문을 확정할 때 시스템이 같은 수량으로 계획을 **직접 다시 계산**하고, 그 결과만 저장한다 | 시스템 설명에 "클라이언트 값은 믿지 않는다"고 적혀 있음 |
| 2 | **확정한 주문은 나중에도 확정 당시 그대로 보인다** | 확정할 때 그때의 기준 정보와 계획안 전체를 주문에 함께 저장한다. 기준 정보를 바꿔도 과거 주문은 바뀌지 않는다 | 시스템 설명("주문 확정 시 그대로 저장된다"), 기준 정보 화면 문구("이미 확정한 주문의 계획은 바뀌지 않습니다") |
| 3 | **본 숫자와 확정되는 숫자가 다르지 않게 한다** | 계획안을 본 뒤 기준 정보가 바뀌었다면 확정을 막고 "다시 시뮬레이션해 주세요"라고 안내한다. 기준 정보를 저장할 때마다 변경 번호를 올려 이를 알아낸다 | 시스템 설명("시뮬레이션 이후 마스터가 바뀌었는지 확인하는 데 쓴다"), 오류 문구 |
| 4 | **여러 사람이 동시에 써도 서로 덮어쓰지 않는다** | 주문 상태를 바꿀 때 "화면을 열었던 시점의 주문 상태"와 현재가 다르면 반영하지 않고 새로 고침 후 다시 시도하도록 안내한다 | 시스템 설명("그 사이 다른 사람이 바꿈"), 오류 문구 |
| 5 | **기준 정보는 일부만 반영된 상태가 되지 않게 한다** | 틀린 값이 하나라도 있으면 **아무것도 저장하지 않고**, 틀린 이유를 **한꺼번에 모아서** 보여 준다 | 시스템 설명("아무것도 저장하지 않고 이유를 모아") |
| 6 | **잘못되면 이유를 그대로 알려 준다** | 입력 오류, 허용되지 않는 상태 변경, 동시 수정 충돌은 사용자에게 이유를 문장으로 보여 준다. 충돌은 "새로 고침 후 다시 시도"로 구분해서 안내한다 | 시스템 설명("사용자에게 이유를 그대로 보여 줄 업무 오류") |
| 7 | **계산이 틀렸다면 계획안을 내놓지 않는다** | 계산 결과를 하루씩 다시 따라가며 검산하고, 싣는 양과 창고 재고가 맞지 않으면 계획을 내놓지 않는다 | 시스템 설명("수거량이 그 시점 재고와 다르면 일정 계산에 오류가 있는 것이다") |
| 8 | **로그인한 사람만 쓰고, 누가 했는지 남긴다** | 로그인하지 않으면 로그인·회원가입 화면만 볼 수 있다. 주문과 상태 변경에는 처리한 사용자의 아이디를 기록한다. 누구나 회원 가입으로 계정을 만들 수 있고 가입한 회원도 같은 방식으로 기록한다 | 시스템 설명("로그인하지 않으면 로그인·회원가입 화면만 볼 수 있다"), 동작 확인 |
| 9 | **기준 정보는 모든 사용자가 같은 값을 본다** | 기준 정보는 사용자별이 아니라 하나만 두고 모두가 공유한다 | 기준 정보 화면 문구("모든 사용자가 같은 값을 봅니다") |
| 10 | **여러 안을 보여 주고 사람이 고른다** | 계획안 3가지(비용 최소 / 가장 빠르게 / 가까운 곳부터)를 항상 함께 보여 주고, 사용자가 하나를 골라 확정한다 | 화면 구성과 동작. 3가지를 정한 이유는 적혀 있지 않음 (→ 아래 Q1) |

## 3. 변경할 때 지킬 것

위 설계 의도에서 이끌어 낸, 앞으로 기능을 바꿀 때 어기면 안 되는 원칙입니다.

1. **확정은 항상 시스템이 다시 계산한 결과로 한다.** 화면이 보낸 금액·날짜를 그대로 저장하지 않는다.
2. **확정한 주문의 내용은 바뀌지 않는다.** 계산 규칙이나 기준 정보를 바꿔도 과거 주문의 날짜와 금액이 달라지면 안 된다.
3. **기준 정보를 바꾸는 모든 방법은 "기준이 바뀌었다"는 표시를 남겨야 한다.** 그래야 오래된 계획안으로 확정하는 것을 막을 수 있다.
4. **주문 상태를 바꾸는 모든 방법은 동시 수정 확인을 거친다.** 새 기능도 같은 방식을 쓴다.
5. **기준 정보 검사는 "전부 맞으면 저장, 하나라도 틀리면 전부 저장 안 함"을 유지한다.**
6. **계산 결과를 검산하는 단계를 끄지 않는다.** 검산에서 문제가 나오면 검산을 우회하지 말고 계산 자체를 고친다.

## 4. 변경할 때 함께 확인할 곳

| 이런 변경을 하면 | 함께 확인할 것 |
|---|---|
| 생산·수거·비용 계산 규칙 변경 | 계산 규칙을 확인하는 자동 테스트, 화면의 규칙 설명 문구, **과거 주문에 미치는 영향** |
| 기준 정보 항목 추가·변경 | 기준 정보 수정 화면, 입력 검사 범위, **주문에 함께 저장되는 값에도 추가했는지**, 주문 상세 화면의 기준 정보 표 |
| 계획안에 보여 주는 항목 변경 | 주문 추가 화면과 주문 상세 화면이 **같은 모양의 데이터를 같은 방식으로** 보여 주고 있으므로 둘 다 확인. 이미 저장된 과거 주문이 새 모양에서도 열리는지 |
| 나라 추가·변경 | 나라 목록, 기본값, 지도 위 위치, 계산 시간 증가 |
| 주문 상태·허용 순서 변경 | 상세 화면의 버튼, 목록의 상태별 보기, 변경 기록 |
| 확정한 뒤에도 고칠 수 있는 값 추가(예: 고객사 이름) | 원칙 2(계획·날짜·금액은 그대로)와 부딪히지 않는지, 고칠 수 있는 상태(확정·진행만), 원칙 4(동시 수정 확인)와 같은 방식을 쓰는지, 사용자가 쓴 문자열을 화면에 그릴 때 이스케이프하는지 |
| 로그인·권한 변경 | 로그인 처리(관리자와 가입한 회원이 같은 방식), 회원 가입 처리, 주문·변경 기록에 남는 작성자 |

## 5. 조정될 수 있는 값

요구사항(PRD)에서는 "한도 안에서", "기본값으로"라고만 쓰고, 실제 숫자는 바뀔 수 있어서 여기에 모았습니다. 이 숫자들의 **업무상 근거는 확인되지 않았습니다**(아래 Q2).

| 항목 | 현재 값 |
|---|---|
| 총 주문 수량 | 1K 이상 100,000K 이하 |
| 배의 수 | 1~4척 |
| 뱃길 일수 | 1~365일 (정수) |
| 하루 최대 생산량, 보관 한도 | 1~1,000,000 (정수, K 단위) |
| 셀 1개 원가 | 1~100,000,000원 (정수) |
| 하루 운항비 | 0원 초과, 원 단위로 떨어지는 값 (화면에서는 억 원 단위로 입력) |
| 공장별 하루 운영비 | 0원 이상, 원 단위로 떨어지는 값 (화면에서는 억 원 단위 소수로 입력, 기본 1억 원) |
| 주문 메모 길이 | 1,000자 이하 |

**처음 시작할 때 들어가는 기본값** (기준 정보가 비어 있을 때만 채워지고, 이후 화면에서 바꿀 수 있음):

| 공장 | 하루 최대 생산 | 보관 한도 | 셀 1개 원가 | 한국까지 뱃길 |
|---|---|---|---|---|
| 중국 | 400K | 4,000K | 700원 | 1일 |
| 일본 | 800K | 2,000K | 900원 | 2일 |
| 베트남 | 200K | 10,000K | 550원 | 5일 |
| 인도네시아 | 300K | 7,000K | 450원 | 7일 |

배는 3척, 한 척의 하루 운항비는 1억 원, 공장별 하루 운영비는 1억 원입니다. 공장 사이 뱃길 6구간도 기본값이 들어 있습니다.

## 6. 의도를 확인할 수 없는 부분

시스템 안에서 의도를 알 수 있는 설명을 찾지 못한 부분입니다. 팀이 확인해서 확정하거나 지워야 합니다.
요구사항을 정하는 질문은 `PRD.md`에, **설계 이유를 묻는 질문은 여기에** 둡니다. 겹치는 질문은 한쪽에만 쓰고 연결했습니다.

**설계 이유를 묻는 질문**

- **Q1.** **"가까운 곳부터" 안은 왜 있는가?** 다른 두 안은 가장 좋은 안을 찾는 방식인데, 이 안만 정해진 규칙대로 한 가지만 만듭니다. 실제 선택지인지 비교용 기준인지 알 수 없습니다.
- **Q2.** **한도(총 수량 100,000K, 배 4척, 뱃길 365일, 메모 1,000자)의 근거**는? 시스템은 모든 경우의 수를 따져 가장 좋은 안을 고르는 방식이라 계산 속도 때문일 수 있지만, 어디에도 적혀 있지 않습니다.
- **Q3.** **기준 정보의 기본값은 처음 한 번만 들어갑니다.** 이미 저장된 값이 있으면 기본값을 바꿔도 반영되지 않는데, 기본값의 "정본"을 어디에 둘 것인지 정해져 있지 않습니다.
- **Q4.** 기준 정보를 **값이 그대로인데 저장만 해도** 변경 번호가 올라갑니다. 그러면 계획안을 보고 있던 다른 사람의 확정이 막히는데, 의도한 것인가?
- **Q5.** **고객사 이름을 확정한 뒤에도 고칠 수 있게 한 것**(2026-10-22 결정)은 의도 2(확정한 주문은 확정 당시 그대로)와 어떻게 어울리는가? 계획·날짜·금액은 바뀌지 않아 어기는 것은 아니지만, 확정 후 바꿀 수 있는 값이 상태와 고객사 이름으로 늘었습니다. 또 고친 사람·일시를 남기지 않는데(의도 8), 사용자가 여러 명이 되면 필요한지 확인이 필요합니다.

**PRD에서 다루는 질문** (여기에 다시 쓰지 않습니다)

| 내용 | 위치 |
|---|---|
| 이 도구를 실제로 누가, 어떤 업무에 쓰는가 | PRD Q1 |
| 취소하면 주문을 삭제하는 것이 의도인가 | PRD Q2, "결함 후보" |
| 회원 가입으로 누구나 계정을 만들고 모두 같은 권한을 갖는 것이 의도한 단순화인가, 임시 상태인가 | PRD Q3 |
| 기준 정보 변경 기록이 필요한가 | PRD Q4 |
| 계산 검산 실패 시 사용자에게 무엇을 보여 줄 것인가 | PRD "결함 후보" |
