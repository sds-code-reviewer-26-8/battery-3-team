# 나의 Loop 설계: 기능 추가 범용 Loop

## 1. 목적과 원칙

**목적**: 어떤 기능을 추가하더라도 **구현 전 점검 → 구현 → 구현 후 검증**을 같은 틀로 수행하되, 기능의 위험에 맞춰 엄격함을 조절한다.

기능은 매번 달라지므로 이 Loop는 특정 기능을 위한 절차가 아니라, **기능을 입력으로 받아 분류하고 처리하는 틀**이다.

**적용 대상**: 이 프로젝트(배터리 주문 관리: Spring Boot, 단위·통합 테스트 JUnit, 화면 테스트 Playwright E2E)

**여섯 가지 원칙**

| # | 원칙 | 뜻 |
|---|---|---|
| 1 | 증거 우선 | 실제로 실행·확인한 것만 적는다. 확인하지 못한 것은 "미확인"으로 적고, 지어내지 않는다. |
| 2 | 기준 먼저 | "끝났다"를 판정할 기준을 **구현 전에** 정한다. 구현 후에 기준을 맞춰 바꾸지 않는다. |
| 3 | 범위 고정 | 정한 범위 밖의 수정이 필요해지면 멈추고 사람에게 묻는다. |
| 4 | 위험에 비례 | 기능을 분류해 위험이 클수록 점검과 승인을 늘린다. |
| 5 | 되돌릴 수 없는 일은 사람이 | 삭제, 외부 공개, 배포처럼 되돌리기 어려운 작업은 사람이 승인한다. |
| 6 | 실패를 숨기지 않는다 | 실패·건너뜀·미확인을 기록하고, 원인을 분류해 알맞은 단계로 되돌아간다. |

## 2. 전체 흐름

```
 기능 요청
    │
    ▼
 [A. 접수·분류] ──→ 등급 L1 / L2 / L3 결정
    │
    ▼
 [B. 사전 검토·세팅]  ← 증거: precheck.html
    │
    ▼
 ◆ HITL ① 구현 착수 승인
    │
    ▼
 [C. 구현]
    │
    ▼
 [D1. 테스트 추가]  통과 기준마다 필요한 단위·통합·E2E TC 추가
    │
    ▼
 [D2. 정적 검사(Lint)]  구현 코드와 테스트 코드 모두
    │
    ▼
 [D3. 실행·판정]  새 TC → 회귀 → (해당 시) 비기능·수동
    │
    ├─ 실패 ──→ 원인 분류 ──→ 알맞은 단계로 되돌아감 (Feedback, 8장)
    ▼
 [E. 리포트 작성]  ← 증거: report.html
    │
    ▼
 ◆ HITL ② 완료 승인 ──→ 완료
```

### 역할 분담 (기본값)

| 단계 | AI가 하는 일 | 사람이 하는 일 |
|---|---|---|
| A. 분류 | 질문에 답해 등급을 제안 | 등급 확인 (애매하면 한 등급 위로) |
| B. 사전 검토 | 근거 조사, 현재 상태 확인, precheck 초안 작성 | **기대 동작·범위·통과 기준 결정**, 게이트 ① 승인 |
| C. 구현 | 정한 범위 안에서 구현 | 범위 밖 수정이 필요할 때 판단 |
| D1. 테스트 추가 | 필요한 TC 작성 | 기존 TC를 고쳐야 할 때 승인 |
| D2·D3. 린트·TC 실행 | 실행하고 결과 파일을 남김 | 결과를 확인하고 이상한 결과를 판단 |
| E. 리포트 | report 초안 작성 (숫자는 결과 파일에서) | **게이트 ② 승인** |

## 3. 기능 분류 (A단계)

기능이 들어오면 다섯 가지 질문에 예/아니오로 답해 등급을 정한다.

| # | 질문 |
|---|---|
| Q1 | 저장된 데이터(DB 구조나 값)를 바꾸는가? |
| Q2 | **되돌리기 어려운 동작**(삭제, 외부 공개, 배포 등)이 포함되는가? |
| Q3 | **기대 동작이 요구사항 문서(PRD)에 정해져 있지 않은가?** |
| Q4 | 세 곳 이상의 화면·기능에 영향을 주는가? |
| Q5 | 금액 계산, 사용자 권한, 보안과 관련되는가? |

| 등급 | 조건 | 성격 |
|---|---|---|
| **L1** | 모두 "아니오" | 가벼운 변경 (문구, 표시, 단순 조회) |
| **L2** | "예"가 1~2개 (Q2, Q3 제외) | 일반 기능 |
| **L3** | Q2 또는 Q3가 "예", 또는 "예"가 3개 이상 | 위험하거나 **사람의 결정이 필요한** 변경 |

**Q2와 Q3를 L3로 올리는 이유**: 되돌릴 수 없는 일과 기대 동작이 정해지지 않은 일은 AI가 혼자 판단해서는 안 되기 때문이다. 기대 동작을 정하는 것은 사람의 몫이다.

**분류가 애매하면 한 등급 위로 올린다.**

## 4. 사전 검토 (B단계)

### 4-1. 모든 기능이 거치는 공통 점검

| 점검 | 확인하는 것 | 증거(precheck.html) |
|---|---|---|
| 근거 확인 | 요구사항(PRD), 설계 의도(INTENT), 프로젝트 안내 문서를 읽고 해당하는 항목을 찾았는가 | 2장 근거 자료 |
| 현재 상태 확인 | 바꾸기 전 모습을 **직접 실행해** 확인했는가 (결함이면 먼저 재현) | 3장 현재 상태 |
| 범위 정의 | 포함할 것과 포함하지 않을 것을 적었는가 | 1장 목표와 범위 |
| 통과 기준(AC) 작성 | 완료를 판정할 기준을 Given/When/Then으로 적었는가 | 6장 통과 기준 |
| 환경·기준선 | 앱이 실행되는가, 기존 테스트가 **지금 몇 개 통과하는지**, 린트(또는 컴파일)의 **현재 에러·경고 수**를 기록했는가 | 5장 환경 점검 |
| 검증 계획 | 통과 기준마다 **어떤 테스트(단위·통합·E2E)로 검증할지** 정했는가 | 6장 통과 기준의 '검증 방법' |
| 영향 범위 | 어떤 파일·화면·테스트가 영향받는가. **호출하는 곳의 개수**와, **화면 구조(컬럼 순서·칸 수)나 값 목록을 정확히 비교하는 테스트**까지 검색으로 찾아 적는다 | 4장 영향 범위 |
| 분류 기록 | 기능 분류(Q1~Q5)와 등급, 근거를 적었는가. 템플릿에 전용 칸이 없으므로 **1장 표에 행으로 추가**한다 (템플릿 구조는 바꾸지 않는다) | 1장 목표와 범위 |

### 4-2. 등급별 추가 점검

| 등급 | 추가로 하는 점검 |
|---|---|
| L1 | 없음 (공통 점검만) |
| L2 | 위험 요소와 대응 적기, 기존 데이터와의 호환 확인(Q1이 예일 때) |
| L3 | **대안 두 가지 이상 비교**, 되돌리는 방법 적기, 영향받는 문서(PRD, INTENT) 목록, 사람이 정할 **기대 동작** 명시 |

### 4-3. 기능 성격별 추가 확인 (해당할 때만)

이 프로젝트에서 지켜 온 설계 원칙을 어기지 않는지 확인한다.

| 성격 | 확인 |
|---|---|
| 계산 규칙을 바꾼다 | 이미 확정된 주문의 내용이 바뀌지 않는가 |
| 주문 확정·상태 변경에 관여한다 | 서버가 다시 계산하는 원칙, 동시 수정 방지가 유지되는가 |
| 기준 정보(마스터)를 바꾼다 | 기준이 바뀌었는지 확인하는 방식이 유지되는가 |
| 화면을 바꾼다 | 기존 E2E 시나리오 중 영향받는 것이 무엇인가 |

## 5. HITL 게이트 (사람이 판단하는 지점)

### 5-1. 항상 거치는 두 게이트

| 게이트 | 시점 | 사람이 확인하는 것 |
|---|---|---|
| **① 구현 착수 승인** | B단계 끝 | 범위가 적절한가, 통과 기준이 구체적이고 검증 가능한가 (L2는 위험 대응, L3는 **기대 동작 결정·대안 선택·되돌리는 방법** 추가) |
| **② 완료 승인** | E단계 끝 | 모든 통과 기준을 충족했는가, 실패·건너뜀이 정직하게 기록되었는가, 기존 기능이 깨지지 않았는가. **보완이 필요하면 해당 단계로 되돌린다(Feedback).** |

### 5-2. 조건부로 추가되는 게이트

| 상황 | 동작 |
|---|---|
| 구현 중 **사전 검토에 없던 범위 밖 수정**이 필요해짐 | 멈추고 사람에게 묻는다 |
| **되돌릴 수 없는 작업**을 실행하기 직전 (데이터 삭제, 원격 반영 등) | 사람이 승인한 뒤에 실행한다 |
| 같은 원인으로 **2회 연속 실패** | 멈추고 사람에게 넘긴다 |

### 5-3. AI가 하지 않는 것
- 승인·결정 칸을 대신 채우지 않는다.
- 기대 동작이 정해지지 않은 부분을 임의로 정하지 않는다.
- 정한 범위를 넓히지 않는다.

## 6. 구현 규칙 (C단계)

- **범위 안에서만** 수정한다.
- **통과 기준 하나씩** 작은 단위로 구현한다. 각 기준에 대응하는 테스트는 구현이 끝난 뒤 D1단계(7-1)에서 추가한다.
- **기존 테스트를 통과시키려고 기존 테스트나 기준을 고치지 않는다.** 고쳐야 한다면 이유와 함께 사람에게 승인받는다.
- 변경한 파일과 이유를 기록한다 (report.html 2장 구현 요약의 근거).
- 기존 코드의 스타일과 이름 규칙을 따른다.
- 구현 중 **사전 검토에 없던 영향**을 발견하면 report.html 6장(남은 이슈와 후속 작업)에 "사전 검토가 놓친 항목"으로 적고, 제안 칸에 다음 사전 검토에 추가할 점검 항목을 적는다. 정한 범위 안이면 직접 확인하고 계속하고, 범위 밖이면 5-2장에 따라 멈추고 사람에게 묻는다.
- **기능마다 별도 브랜치**에서 작업한다. 완료 승인(게이트 ②) 뒤에 PR로 반영하며, 저장소 규칙상 `main`에 직접 push하지 않는다. (push와 PR은 사람이 요청할 때 한다.)
- 기능이 **요구사항(PRD)이나 설계 의도(INTENT)에 영향을 주면 문서도 같은 변경에 포함해 갱신**한다. 기대 동작을 바꾸는 갱신은 사람이 승인한다.

## 7. 구현 후 테스트 추가와 검증 (D단계)

구현이 끝나면 D단계를 세 부분으로 진행한다: **D1 테스트 추가 → D2 정적 검사(Lint) → D3 실행·판정**.

> D1~D3(테스트 추가, 린트 검사, 실행)는 **나의 Loop에서 추가한 단계**다. 팀 공통 템플릿(precheck.html, report.html)은 그대로 쓰고, 이 단계의 결과는 report.html의 기존 항목(검증 결과 표)에 행으로 남긴다.

### 7-1. D1. 테스트 추가 (구현이 끝난 뒤)

통과 기준(AC)을 검증할 테스트(TC)를 추가한다. 어떤 계층의 테스트를 추가할지는 **바뀐 것의 성격**으로 정한다.

| 바뀐 것의 성격 | 추가할 테스트 | 예 |
|---|---|---|
| 계산·규칙·서버 로직 | 단위 테스트 (JUnit) | 경로 계산 규칙 |
| 서비스와 저장소가 함께 동작하는 흐름 | 통합 테스트 | 주문 확정, 상태 변경 |
| 화면 동작, 사용자 흐름, 화면 문구 | E2E 테스트 (Playwright) | 로그인, 주문 목록, 확정 흐름 |

규칙
- **통과 기준(AC)마다 TC가 하나 이상** 대응한다. TC 이름에 AC 번호(또는 시나리오 ID)를 넣어 서로 찾을 수 있게 한다.
- **가장 낮은 계층에서 확인할 수 있으면 그 계층의 TC만 추가한다.** 단위 테스트로 충분한 규칙을 E2E로 중복하지 않는다. 사용자가 화면에서 보는 흐름이 바뀌면 E2E를 추가한다.
- E2E 시나리오 목록(문서)이 있으면 새 시나리오도 함께 추가한다.
- **새 TC가 실제로 기능을 검증하는지 확인한다** (L2·L3). 가능하면 구현 이전 코드에서 새 TC가 **실패하는지** 본다. 구현 전에도 통과한다면 그 TC는 기능을 검증하지 못하는 것이다.
- 구현 이전 코드에서의 확인은 **계층마다 의미가 다르다.** 화면·HTTP 수준 TC(E2E)는 실제로 실패하는지를 본다. 단위·통합 TC가 **새로 만든 코드를 직접 참조하면 이전 코드에서는 컴파일이 되지 않는다.** 이 경우는 "구현 없이는 통과할 수 없다"로만 기록하고, 동작 확인은 하지 못했다고 report에 적는다.
- **브라우저가 입력 자체를 막는 규칙**(예: 입력칸의 최대 길이 제한)은 서버 검증을 통합 테스트로 확인하고, 화면에서 오류가 어떻게 보이는지는 확인하지 못했다고 report 5장에 기록한다.
- 기존 TC를 고쳐야 하면 6장 규칙대로 사람에게 승인받는다.
- 앱 실행이나 DB 상태를 바꾸는 TC는 **정리(원복) 방법**을 함께 정한다.

### 7-2. D2. 정적 검사 (Lint)

추가·변경한 **구현 코드와 테스트 코드 모두**를 검사한다.

| 항목 | 내용 |
|---|---|
| 대상 | 변경한 Java 코드, 추가·변경한 테스트 코드(TypeScript) |
| 현재 상황 | 이 프로젝트에는 **린트 도구가 설정되어 있지 않다.** (Java 빌드 설정과 E2E 폴더를 확인함) E2E(TypeScript) 폴더에는 **타입 검사 도구도 없다.** |
| 도구가 있을 때 | 설정된 도구를 사용한다. |
| 도구가 없을 때 | **"린트 미설정"이라고 기록**하고, 컴파일(빌드)과 타입 검사로 대신한다. **타입 검사 도구도 없는 영역**(이 프로젝트의 E2E)은 **"미확인"으로 기록**한다. 도구를 새로 도입하는 일은 **별도 기능으로 분류**해 이 Loop로 처리한다. |
| 기준선 | B단계에서 바꾸기 전의 에러·경고 수를 기록해 둔다. |
| 판정 | **에러 0** 필수. 새로 생긴 경고는 해결하거나 사유를 기록한다. 경고 수가 기준선보다 늘어나지 않아야 한다. |
| 주의 | 자동 수정 기능을 쓰면 **범위 밖 파일이 바뀌지 않았는지** 확인한다 (범위 고정 원칙). |

### 7-3. D3. 실행과 판정

| 순서 | 계층 | 내용 |
|---|---|---|
| ① | 기준선 | 변경 **전** 상태를 기록한다 (B단계에서 측정). 이후 비교의 기준이 된다. |
| ② | 새 TC 실행 | D1에서 추가한 TC를 실행해 통과 기준(AC)을 하나씩 확인한다. |
| ③ | 회귀 | 기존 기능이 깨지지 않았는지 기존 테스트로 확인한다. |
| ④ | 비기능·수동 확인 | 해당할 때만 (성능, 화면 직접 확인, 데이터 확인) |

**등급별 필수 범위 (기본값)**

| 등급 | 테스트 추가 (D1) | 린트 (D2) | 실행 범위 (D3) |
|---|---|---|---|
| L1 | 필요한 경우만. 기존 동작 확인으로 충분하면 생략하고 **사유를 기록** | 변경한 파일 | 새 TC(있으면) + 관련 테스트 + 단위 테스트 전체 |
| L2 | **AC마다 TC 추가** | 변경한 파일 + 빌드 | 새 TC + **기존 테스트 전체**(단위·통합·E2E) |
| L3 | 필요한 계층(단위·통합·E2E) **모두** | 변경한 파일 + 빌드 | 새 TC + 기존 테스트 전체 + **수동 확인** + 데이터·환경 확인 |

**판정 규칙**
- **통과**: 다음을 모두 만족한다.
  - 모든 통과 기준을 충족하고, **각 기준에 대응하는 TC가 있으며 통과**한다.
  - 회귀 실패가 0이다.
  - **린트 에러가 0**이다 (린트 미설정이면 컴파일·타입 오류 0).
  - **이유 없는 건너뜀이 없다.**
- 건너뛴 항목은 **이유와 함께** 기록한다. 이유를 적지 못하는 건너뜀은 미통과로 본다.
- 전체 실행에서 **조건 때문에 건너뛴 테스트**(예: 깨끗한 DB가 필요한 테스트)는 조건을 갖춘 환경에서 **따로 실행해 보완**하고, 전체 실행에서는 건너뛰었다는 사실도 함께 기록한다.
- 실행 환경(앱 실행 방식, DB 상태)도 함께 기록한다. 같은 테스트도 환경에 따라 결과가 달라진다.
- **기존 데이터를 지우지 않는다.** 깨끗한 DB가 필요한 검증은 인메모리 DB처럼 **격리된 환경**에서 실행한다. 개발 DB를 지우는 일은 되돌릴 수 없는 작업이므로 사람이 승인한다.

## 8. 피드백 규칙 (실패했을 때)

**원인을 확인하지 않고 재실행하거나, 기준을 낮춰서 통과시키지 않는다.** 실패하면 먼저 원인을 분류하고, 그에 따라 되돌아갈 단계를 정한다.

| 실패 원인 | 되돌아가는 곳 | 이 프로젝트에서의 예 |
|---|---|---|
| **구현 오류** (앱이 잘못됨) | C. 구현 | 기대 값과 실제 값이 다름 |
| **검증 방법 오류** (앱은 맞는데 테스트가 틀림) | D. 검증 방법 수정 (사람에게 보고) | 로그인 실패 뒤 주소에 세션 번호가 붙는 것을 가정하지 않아 실패, 같은 값을 읽는 방식이 달라 실패 |
| **환경·데이터 문제** | B. 환경 점검 | 주문이 이미 쌓여 있어 "주문 없음" 화면을 확인할 수 없음 |
| **Lint 오류** (컴파일·타입 오류 포함) | C. 구현 (범위 안에서 수정) | 변경한 코드의 규칙 위반, 타입 오류 |
| **새 TC가 구현 이전에도 통과** (TC가 기능을 검증하지 못함) | D1. 테스트 보강 | 기대 값이 느슨하거나 엉뚱한 곳을 확인함 |
| **기준(AC) 자체가 부적절하거나 기대 동작이 미정** | B. 사전 검토 → 게이트 ① 다시 | 기대 동작을 사람이 정하지 않은 채 구현함 |
| **요구사항과 충돌** | 사람에게 넘김 | PRD와 현재 동작이 다름 |

## 9. 반복 한도와 중단 조건 (기본값)

**반복** = 검증에서 실패하거나 사람이 게이트에서 반려해 이전 단계로 되돌아간 횟수.

| 구분 | 규칙 |
|---|---|
| 최대 반복 | **3회** |
| 성공으로 끝내는 조건 | 7-3의 통과 조건 충족 + 게이트 ② 승인 |
| **중단하고 사람에게 넘기는 조건** | ① 3회 초과 ② 같은 원인 2회 연속 실패 ③ 범위 밖 수정이 필요해짐 ④ 환경 문제를 해결할 수 없음 ⑤ 되돌릴 수 없는 작업이 필요해짐 |

중단할 때는 **어디까지 했고 무엇이 막혔는지**를 report.html에 남긴다.

## 10. 증거 (Evidence)

| 단계 | 증거 문서 | 주요 내용 |
|---|---|---|
| B. 사전 검토 | `precheck.html` | 목표·범위, 근거, 현재 상태, 영향·위험, 환경, **통과 기준**, 반복 한도, HITL ① |
| E. 리포트 | `report.html` | 구현 요약, **검증 결과(통과 기준과 1:1 대조)**, 반복 기록, 건너뜀·미확인, 증거 파일, HITL ② |

- 두 문서는 **통과 기준(AC)으로 연결**된다. precheck에서 정한 기준을 report가 하나씩 대조한다.
- 검증 결과의 숫자는 **테스트 결과 파일에서 가져온다**. 손으로 적거나 추정하지 않는다.
- **추가한 TC의 목록(통과 기준과의 대응)**과 **린트 결과**(도구, 에러·경고 수, 기준선과의 비교)는 report.html 3장에 **별도 표로 추가**해 남긴다. 통과 기준 표에 행으로 섞으면 요약의 자동 집계("충족한 통과 기준")가 흐려진다. 팀 공통 템플릿의 구조는 바꾸지 않는다.
- 요약의 자동 집계는 **통과 기준 표만** 센다. 통과 기준 밖의 건너뜀·미확인은 5장에 따로 적히므로, 요약의 "건너뜀·미확인 0"을 "문제 없음"으로 읽지 않는다. (report에 이 점을 문구로 명시한다.)
- 린트·컴파일의 **기준선**은 precheck.html 5장 환경 점검에 적는다.

### 10-1. 증거 저장 위치

작업 하나(Loop 한 번)마다 폴더 하나를 만들어 증거를 모은다.

```
docs/evidence/{이름}/{작업번호 + 작업명}/
├── precheck.html     B단계 사전 검토
├── report.html       E단계 검증 리포트
└── results/          테스트 결과 파일, 컴파일·린트 로그, 스크린샷 등 증거 파일
```

| 항목 | 규칙 |
|---|---|
| `{이름}` | 팀원 이름 (예: 우주상) |
| `{작업번호 + 작업명}` | 작업마다 자유롭게 정하되 **번호를 앞에** 둔다. 예: `TASK-001-bugfix`, `TASK-002-customer-name` |
| 템플릿 | 팀 공통 템플릿(`docs/loops/templates/precheck.html`, `report.html`)을 이 폴더로 복사해 채운다. |
| 파일 경로 표기 | report.html 7장(증거 파일 목록)에는 이 폴더 기준 상대 경로(예: `results/after-e2e.json`)로 적는다. |
| 같은 작업을 다시 돌릴 때 | 같은 폴더에서 갱신하고, 되돌아간 이력은 report.html 4장(반복 기록)에 남긴다. |
