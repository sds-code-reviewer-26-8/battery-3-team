# code-explain-mission1

`$ARGUMENTS`로 받은 대상의 코드를 분석해서, 쉽게 이해할 수 있는 HTML 파일 하나를 만든다.

## 1. 범위 정하기

- `$ARGUMENTS`가 비어 있으면 "무엇을 이해하고 싶은지"(전체 / 패키지 / 파일 / 기능명) 한 번만 묻는다.
- 해석 규칙
  - `전체`: 저장소의 소스 전체(빌드 산출물, `.gradle`, `.idea`, `data/` 제외)
  - 패키지: 해당 패키지 디렉토리 전체
  - 파일: 그 파일과, 그 파일이 직접 호출하거나 호출당하는 핵심 파일
  - 기능명(예: "주문 확정"): 그 기능의 진입점(컨트롤러/화면)부터 서비스, 저장소, 계산 로직, 화면 스크립트까지 따라가며 관련 파일을 모은다
- 범위를 어떻게 해석했는지는 HTML 맨 위에 한 줄로 밝힌다.

## 2. 코드 읽기 (가장 중요)

- 설명에 쓸 파일은 **실제로 읽는다**. 읽지 않은 파일에 대해 내용을 지어내지 않는다.
- 읽지 못했거나 이름·참조 관계로 추정한 내용은 HTML에 `추정` 또는 `미확인` 배지를 붙여 구분한다.
- 근거가 되는 위치는 `파일명:줄번호` 형태로 남긴다.
- 테스트가 있으면 규칙의 근거로 활용하고, 테스트가 없는 영역은 리뷰 포인트에 반영한다.
- 범위가 크면 Explore 에이전트로 조사를 나눠도 된다. 단, 최종 HTML의 내용 책임은 이 스킬을 실행하는 쪽에 있다.

## 3. HTML 요구사항

### 공통
- **단일 HTML 파일.** CSS와 JS를 모두 인라인으로 넣고, 외부 CDN·폰트·이미지를 쓰지 않는다(오프라인으로 열려야 한다). 다이어그램은 인라인 SVG 또는 CSS로 그린다.
- UI 컨셉: **밝고 깔끔한 카드형**. 여백을 넉넉히, 강조색은 1가지(+ 상태색 Green/Yellow/Red), 본문 글자는 읽기 편한 크기. `prefers-color-scheme: dark`도 지원한다.
- 핵심 위주로 쓴다. 코드를 길게 붙여 넣지 말고, 필요하면 3~8줄 발췌만 넣는다. 반복·장황한 설명 금지.
- 모바일 폭에서도 가로 스크롤 없이 읽힌다.
- 상단에 제목, 대상, 분석 일자, 범위 해석 한 줄을 보여 준다.

### 탭 5개
1. **한눈에 보기** — 이 코드가 하는 일
2. **사용자 흐름** — 요청이 어디서 시작해 어디로 흘러가는지
3. **구조** — 모듈/클래스 관계, 의존성
4. **핵심 규칙** — 도메인 규칙, 예외 처리
5. **리뷰 포인트** — 위험해 보이는 곳, Green/Yellow/Red 영역 표시

### 설명 모드 토글 (탭마다 독립)
각 탭 안에 `3줄 요약 / 비개발자용 / 개발자용` 세 모드 토글을 둔다. 같은 내용을 모드별로 다르게 쓴다.
- **3줄 요약**: 정확히 3줄.
- **비개발자용**: 코드 용어 없이, 중학생도 이해할 비유와 일상 표현. 파일명·클래스명 금지.
- **개발자용**: 파일명·클래스·메서드·줄번호 포함, 정확한 용어 사용.

선택한 모드는 탭을 바꿔도 각 탭별로 유지한다. 기본값은 3줄 요약이다. 모드별 본문을 JS 데이터 객체로 두고 렌더링해도 되고, 모드별 섹션을 숨김/표시해도 된다.

### 인터랙티브 기능 (탭별 최소 요건)
- **한눈에 보기**: 핵심 개념 카드를 눌러 펼치면 한 줄 설명과 관련 파일이 나온다.
- **사용자 흐름**: 단계(화면 → API → 서비스 → 계산/저장 → 응답)를 "다음/이전" 버튼 또는 단계 클릭으로 하나씩 따라가며, 현재 단계의 설명과 담당 파일이 강조된다. 흐름이 여러 개면 선택 드롭다운을 둔다.
- **구조**: 노드(클래스/모듈)를 클릭하거나 올리면 그 노드와 직접 연결된 의존성만 강조하고 나머지는 흐리게 한다. 계층(화면/컨트롤러/서비스/계산/저장)별로 구분해 배치한다.
- **핵심 규칙**: 규칙 목록에 "규칙 / 예외·에러" 필터를 두고, 항목을 누르면 근거(`파일:줄`)와 관련 테스트가 펼쳐진다. 규칙마다 테스트로 검증되는지 표시한다.
- **리뷰 포인트**: Green/Yellow/Red 필터 버튼과 개수 표시. 항목을 누르면 이유와 근거 위치가 펼쳐진다.
- 위 외에도 이해에 도움이 되면 용어 툴팁, 검색 같은 것을 추가해도 되지만, 핵심을 가리면 안 된다.

### 리뷰 포인트 판정 기준
- **Green**: 테스트가 있고 단순하며 의도가 분명한 영역
- **Yellow**: 동작은 맞아 보이나 테스트가 부족하거나, 의도·규칙이 불분명하거나, 변경 시 영향 범위가 큰 영역
- **Red**: 오류·데이터 불일치·보안·동시성·성능 위험이 코드에서 확인되는 영역
- 모든 항목에 **근거(`파일:줄`)와 이유 한 줄**을 붙인다. 근거 없이 Red로 두지 않는다. 확인하지 못한 걱정은 Yellow에 `추정` 배지와 함께 둔다.

## 4. 저장 위치와 파일명

```
./docs/understand/{이름}/code_explain_{대상}_{날짜}.html
```

- `{이름}`: 현재 git 브랜치가 `a/b` 형태면 `b`(예: `mission1/hgkim` → `hgkim`), 아니면 `git config user.name`. 둘 다 없으면 `shared`.
- `{대상}`: `$ARGUMENTS`를 파일명으로 쓸 수 있게 정리한 값(공백은 `_`, 경로 구분자와 특수문자 제거). 한글은 그대로 둬도 된다.
- `{날짜}`: `YYYYMMDD`(오늘).
- 폴더가 없으면 만든다. 같은 이름의 파일이 이미 있으면 덮어쓴다.
- 이 파일은 기록용 산출물이다. 소스 코드는 수정하지 않는다.

   - Windows PowerShell: `Start-Process "<절대경로>"`
   - macOS: `open "<경로>"`, Linux: `xdg-open "<경로>"`
2. 사용자에게는 아래만 짧게 알린다.
   - 저장 경로
   - 범위를 어떻게 해석했는지
   - 읽지 못해 `추정`으로 표시한 부분이 있으면 그 목록
   - Red 항목이 있으면 개수와 한 줄 요약
