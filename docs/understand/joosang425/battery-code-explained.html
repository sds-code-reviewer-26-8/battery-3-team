배터리 주문 관리: 코드 이해 가이드

해외 공장에서 배터리 셀을 싣고 오는 최적 경로를 계산해 주문으로 확정하는 웹 앱을, 코드 기준으로 설명합니다. 그림의 노드와 버튼을 눌러 보세요.

요약기술 스택구조도핵심 흐름 미니 데모용어집Planner알아 둘 점파일 지도

1. 한 줄 요약

나라별 필요 수량(K = 1,000셀)을 입력하면 경로 3가지(운항비 최소 / 가장 빠르게 / 가까운 곳부터)를 계산해 보여 주고, 하나를 골라 주문으로 확정하면 DB에 저장합니다. 확정된 주문은 확정 → 진행 → 완료(중간 취소 가능)로 상태가 바뀝니다.

공장은 중국·일본·베트남·인도네시아 4곳, 도착지는 한국입니다.

3. 구조도

화살표는 호출 방향입니다. 노드를 클릭하면 역할이, 마우스를 올리면 연결된 것만 강조됩니다. (키보드: Tab으로 이동, Enter/Space로 선택)

※ 점선 박스 simulation 패키지는 DB·Spring을 모르는 순수 계산 코드입니다.

4. 핵심 흐름

사용자 행동 하나를 따라가며 위 구조도 위에서 재생합니다. (← → 방향키로도 이동)

위 구조도의 강조 표시가 단계마다 바뀝니다. 구조도가 화면 밖이면 구조도로 이동하세요.

5. 값을 바꿔 보는 미니 데모: 방문 횟수와 싣는 양

주문 수량을 바꾸면 Planner.visits 와 Planner.amounts 가 어떻게 계산하는지 같은 규칙으로 재현합니다.

  • 방문 횟수 = 올림(주문 ÷ 재고 상한)
  • 마지막 방문 전까지는 재고 상한만큼, 마지막 방문은 나머지를 싣습니다.
  • 각 방문분을 채우는 데 필요한 최소 생산 일수 = 올림(싣는 양 ÷ 하루 최대 생산량) (schedule의 ceilDiv)

나라방문 횟수방문별 싣는 양 (K)방문별 최소 생산일생산 원가

단순화: 실제 schedule은 같은 나라를 다시 방문할 때 직전 수거일부터 생산일을 더하고, 배의 이동 시간과 출항일까지 함께 맞춥니다. 이 데모는 방문 한 번을 독립으로 보고 최소 생산 일수만 보여 줍니다. 기준값은 BatteryService.initDefaults()의 기본값입니다.

7. 가장 어려운 부분: Planner

simulation/Planner.java (419줄)는 주문 수량으로 경로 3가지를 계산합니다. 규칙부터 보면 이렇습니다.

규칙

  • 0일차에 모든 공장이 동시에 생산을 시작합니다. 하루 생산 = min(하루 최대, 재고 상한 − 재고, 남은 주문)
  • 배는 도착 시점의 재고를 모두 가져갑니다. 한 나라는 한 척의 배만 방문합니다.
  • 여러 번 수거할 때는 한국에 들러 내려놓고 다시 출항합니다(왕복을 나눔).
  • 배는 재고가 채워지는 날에 맞춰 가능한 한 늦게 출항합니다. 한국에서의 대기는 무료입니다.

단계

  1. 묶기 partitions: 나라를 최대 (배 척수)개 묶음으로 나누는 모든 경우. 한 묶음 = 배 한 척.
  2. 왕복 구성 groupStructures: 방문 횟수가 적은 나라는 어느 왕복에 들를지 FRONT / BACK / SPREAD 패턴을 바꿔 가며 후보를 만들고, 왕복 안 순서는 shortestOrder가 모든 순열 중 항해 일수가 가장 짧은 것을 고름.
  3. 일정 계산 schedule: 방문지마다 재고가 찰 때까지의 날짜를 구해 출항일을 정함.
  4. 선택: 모든 후보 중 COST(운항비 최소, 동률이면 빠른 쪽), FAST(일수 최소, 동률이면 저렴한 쪽). NEAR는 탐색 없이 nearest가 휴리스틱으로 한 번에 만듦.
  5. 검증 toPlan → simulateFactory: 하루씩 생산·수거를 재현하며 수거량과 재고가 다르면 예외. 계산 결과의 자체 검산입니다.
// Planner.java: 방문 횟수
result.put(c, q <= 0 ? 0 : (q + limit - 1) / limit);   // 올림(q / limit)

완전 탐색이라 나라·배 수가 늘면 급격히 느려집니다. 현재 공장 4곳·배 4척 이하라 문제없습니다.

8. 알아 둘 점

  • 로그인: 계정이 admin/admin 하드코딩(AppController.ACCOUNT)이고 세션 방식입니다. LoginInterceptor는 로그인 여부만 확인하며 역할 구분이 없어 로그인한 누구나 마스터 데이터를 고칠 수 있습니다.
  • 서버가 다시 계산: 주문 확정 시 클라이언트가 보낸 계획은 믿지 않고 서버가 같은 입력으로 재계산합니다.
  • 두 가지 충돌 방지: ① 시뮬레이션 후 마스터가 바뀜(masterVersion), ② 동시에 상태 변경(Order version). 둘 다 409로 응답합니다.
  • 취소하면 주문이 삭제됩니다: changeStatus는 CANCELED가 되면 이력은 남기고 주문 행을 delete합니다.
  • 기본값 vs DB: initDefaults()는 설정이 비어 있을 때만 실행됩니다. data/ 폴더(H2 파일)가 남아 있으면 코드의 기본값을 바꿔도 반영되지 않습니다.
  • 마스터 수정 이력은 없음: 버전 번호만 올라갑니다. 다만 각 주문은 확정 당시 Master를 통째로 저장합니다.
  • 코드만으로는 알 수 없음: 운영 배포 방식, 실제 사용자 수.
