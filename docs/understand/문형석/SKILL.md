# understand — 코드 이해용 HTML 가이드 만들기

코드를 처음 읽는 팀원이 **지도처럼** 훑어볼 수 있는 외부 의존 없는 HTML 파일 하나를 만든다.

## 인자
- `$ARGUMENTS` 가 있으면 그 경로/모듈/주제만 다룬다. 없으면 프로젝트 전체.

## 절차

1. **범위 파악** — `CLAUDE.md`, 빌드 파일(`build.gradle.kts` 등), 디렉터리 트리를 먼저 본다. 패키지/계층과 진입점을 찾는다.
2. **핵심 코드 읽기** — 컨트롤러 → 서비스 → 도메인/계산 로직 → 엔티티 순으로 실제 파일을 읽는다. 큰 파일은 공개 메서드와 주석(Javadoc) 위주로 읽고, 알고리즘은 본문까지 따라간다. 추측으로 쓰지 않는다.
3. **테스트 확인** — 테스트 파일 이름과 개수로 무엇이 검증되는지 파악한다. 테스트 통과 여부를 적으려면 실제로 실행한 결과만 쓴다.
4. **HTML 작성** — 아래 구성과 규칙을 따른다.
5. **저장 위치 결정** — `docs/understand/<작성자 이름>/code-guide.html`. 작성자 폴더는 `docs/understand/` 아래 기존 폴더가 있으면 그 사용자의 것을 쓰고, 불분명하면 사용자에게 한 번 묻는다. 팀원별 폴더를 써서 파일 충돌을 피한다.
6. **열어 보여주기** — 사용자가 원하면 기본 브라우저로 연다 (Windows PowerShell: `Start-Process "<경로>"`).
7. **커밋은 요청받았을 때만** 한다. push 는 명시적 요청 없이 하지 않는다.

## 페이지 구성 (해당하는 것만)

1. **한눈에 보기** — 앱이 무엇을 하는지 3~5문장, 기술 스택 태그.
2. **계층 구조도** — 인라인 SVG. 브라우저 → 컨트롤러 → 서비스 → (계산 로직 / 저장소) 처럼 실제 의존 방향대로.
3. **파일 지도** — 경로·줄 수·역할 표. 화면/스크립트 리소스 포함.
4. **요청 흐름** — 핵심 시나리오를 번호 단계로 (예: 입력 → API → 서비스 → 저장). 인증·오류 처리 경로 포함.
5. **도메인·데이터** — 엔티티, 기본 데이터 표, 상태 전이.
6. **핵심 알고리즘** — 규칙, 단계, 비용/수식. 가능하면 **손으로 따라간 작은 예시**.
7. **안전장치** — 검증, 락, 버전 검사 등 설계 의도.
8. **테스트** — 클래스별 개수와 목적.
9. **읽다가 눈에 띈 점** — 의도와 어긋나 보이는 코드, 보안/성능 우려. 단정하지 말고 "확인 필요"로 쓴다.

## 규칙

- **단일 파일**: CSS/JS/SVG 전부 인라인. 외부 CDN·폰트 금지. 한국어 UI.
- **라이트/다크 모두 지원**: 색은 `:root` 변수로 정의하고 `@media (prefers-color-scheme: dark)` 에서 재정의. `body` 에 배경색 명시.
- **모바일 폭에서도 읽히게**: 사이드 목차는 좁은 화면에서 위로 접고 가로 스크롤이 생기지 않게 한다.
- **좌측 고정 목차 + 섹션 앵커**.
- 코드/식별자는 `<code>`, 수식·명령은 `<pre><code>`.
- **검증하지 않은 것을 사실처럼 쓰지 않는다.** 손으로 계산한 값, 실행해 보지 않은 동작은 그렇다고 페이지에 명시한다. 테스트 결과는 실제로 돌린 경우에만 적는다.
- 코드를 수정하지 않는다. 이 스킬의 산출물은 문서 파일 하나다.
- 기준 커밋(`git rev-parse --short HEAD`)을 머리말에 적어, 문서가 어느 시점 코드 기준인지 알 수 있게 한다.
