Battery 코드 가이드

배터리 해상 운송 주문·경로 시뮬레이션 앱을 처음 읽는 사람을 위한 지도. 기준: feature/dev 브랜치 46d3809 (코드는 main 초기 커밋과 동일, 이후 커밋은 문서·설정만).

1. 한눈에 보기

한국(KOREA)이 목적지이고, 중국·일본·베트남·인도네시아 4개 공장이 배터리 셀을 만든다. 사용자는 나라별 주문 수량(단위 K = 1,000셀)을 입력하고, 앱은 배를 어떻게 보낼지 경로 3가지를 계산해 보여준다. 하나를 고르면 주문이 확정되어 저장된다.

COST · 운항비 최소

배의 총 항해일수 × 일 운항비가 가장 작은 계획. 같으면 더 빨리 끝나는 쪽.

FAST · 가장 빠르게

모든 배가 한국에 돌아오는 날(totalDays)이 가장 이른 계획. 같으면 운항비가 낮은 쪽.

NEAR · 가까운 곳부터

한국에서 가까운 나라부터 배에 돌려가며 배정하는 단순 휴리스틱. 탐색 없이 한 가지만 만든다.

2. 계층 구조

핵심 설계: 계산(Planner)은 DB에서 분리되어 있다. 서비스가 DB의 마스터 값을 Master record 로 복사해 넘기므로, Planner는 단위 테스트에서 DB 없이 돌 수 있다.

4. 요청 흐름

A. 시뮬레이션 → 주문 확정

  1. GET /orders/new — 컨트롤러가 현재 Master(버전 포함)를 모델에 넣어 화면을 그린다.
  2. 사용자가 수량을 넣으면 order-new.js 가 POST /api/simulate 호출 → BatteryService.simulate 가 수량 검증(음수 불가, 합계 1 이상 100,000K 이하) 후 Planner.plan 실행.
  3. 응답은 SimulationResult(master, orders, visits, options[3]). 화면이 3경로를 비교해 보여준다.
  4. 경로를 고르고 POST /api/orders (orders, routeType, masterVersion, memo) 호출.
  5. confirm 은 클라이언트가 보낸 계획을 믿지 않고 같은 입력으로 서버에서 다시 계산한다. 그 사이 마스터 버전이 바뀌었으면 409 로 거부.
  6. Order 저장(계획 전체를 planJson 에 JSON 으로) + 상태 이력 1건(null → CONFIRMED) 저장.

화면 쪽 동작 (order-new.js)

  • 공장 4개마다 게이지(슬라이더 + 숫자 입력)가 있고, 아래에 "방문 N회"(= ceil(수량 / 재고 상한))를 바로 보여준다. 재고 상한은 시작 시 GET /api/master 로 받는다.
  • "총 수량"을 바꾸면 even() 이 4개 공장에 균등 분배한다(나머지는 앞쪽 공장부터 1씩).
  • 입력이 바뀌면 invalidate() 가 이전 시뮬레이션 결과를 숨긴다 — 현재 입력과 다른 결과로 확정하는 것을 화면에서도 막는다.
  • 결과 렌더링은 PlanView(요약·표), 지도 위 배 이동은 BatteryAnim(좌표는 map.png 픽셀 기준, 기본 2일/초)이 맡고, 주문 상세 화면도 같은 코드를 재사용한다.

B. 인증

LoginInterceptor 가 /login, /css, /js, /images, /error 를 제외한 모든 요청에서 세션의 loginUser 를 확인한다. 없으면 화면은 /login 으로 리다이렉트, /api/* 는 401. 계정은 admin / admin 하나가 컨트롤러에 하드코딩되어 있다.

C. 마스터 데이터 수정

POST /master → updateMaster 가 모든 입력값을 검증하며 오류를 모은다. 하나라도 틀리면 아무것도 저장하지 않고 오류 목록을 화면에 돌려준다. 성공하면 masterVersion 을 1 올린다(이전 시뮬레이션 무효화 신호).

6. Planner 알고리즘

생산·수거 규칙

  • 0일차에 모든 공장이 동시에 생산을 시작한다. 하루 생산 = min(하루 최대, 재고 상한 − 현재 재고, 남은 주문).
  • 배는 도착 시점의 재고를 전부 가져간다. 재고가 가득 차면 생산이 멈추므로, 주문이 재고 상한보다 크면 여러 번 방문해야 한다.
  • 방문 횟수 = ceil(주문 / 재고 상한). 마지막 방문 전까지는 재고 상한만큼, 마지막은 나머지를 싣는다 (amounts()).
  • 여러 번 수거하는 나라가 있으면 배는 한국에 들러 내려놓고 다시 출항한다(왕복을 나눈다). 한국에서의 대기는 무료.
  • 배는 재고가 찰 때까지 기다리지 않도록 가능한 한 늦게 출항한다.

plan() 의 단계

  1. 나라 분할 — 주문이 있는 나라들을 최대 min(배 수, 나라 수) 개의 묶음으로 나누는 모든 방법을 만든다 (partitions). 묶음 하나 = 배 한 척 담당.
  2. 왕복 구성 — 묶음마다 필요한 왕복 수는 그 안에서 방문 횟수가 가장 많은 나라 기준. 방문 횟수가 적은 나라는 어느 왕복에 넣을지 FRONT / BACK / SPREAD 세 패턴을 모두 시도 (groupStructures). 왕복 안의 방문 순서는 항해일수가 가장 짧은 순열 (shortestOrder).
  3. 일정 계산 — 후보마다 schedule() 이 출항일을 정한다. 각 방문지에서 이전 수거일 + ceil(싣는 양 / 하루 최대) 이후에 도착하도록 출항일을 맞춘다.
  4. 선택 — 모든 후보 중 운항비 최소(COST)와 완료일 최소(FAST)를 뽑는다. NEAR 는 탐색 없이 nearest() 한 가지만 계산.
  5. 일별 시뮬레이션 — 뽑힌 3개에 대해 simulateFactory 가 하루씩 생산·재고·수거를 재현해 그래프용 배열을 만들고, 수거량이 그날 재고와 다르면 예외를 던져 일정 계산 버그를 스스로 검출한다.

비용 공식

생산비 = Σ 나라별 (주문K × 1000 × 셀당 원가)
운항비 = Σ 배별 (항해일수 합 × 일 운항비)      ← 한국 대기·정박은 무료
총비용 = 생산비 + 운항비
복잡도 주의 탐색은 분할 × 패턴 조합 × 순열을 전부 열거하는 완전 탐색이다. 공장이 4개·배가 3척 수준에선 작지만, 나라 수나 방문 횟수가 늘면 급격히 커진다.

7. 계산 예시

기본 마스터에서 중국 5,000K 하나만 주문하면 (손으로 따라간 값):

  1. 방문 횟수 = ceil(5000/4000) = 2, 싣는 양 = [4000, 1000]. 나라가 1개라 배도 1척만 쓴다.
  2. 1차 방문: 4,000K 를 채우려면 4000/400 = 10일. 한국→중국 1일이므로 9일차 출항, 10일차 도착, 11일차 귀환.
  3. 2차 방문: 10일차 수거 직후부터 다시 생산. 1,000K 는 ceil(1000/400) = 3일 → 13일차 이후 도착. 배는 11일차에 귀환해 있으므로 12일차 출항, 13일차 도착, 14일차 귀환.
  4. 총 14일. 항해일수 2+2 = 4일 × 1억 = 운항비 4억. 생산비 = 5000 × 1000 × 700원 = 35억. 합계 39억.

위 숫자는 알고리즘을 읽고 손으로 계산한 값이며, 앱이나 테스트를 실행해 확인한 값은 아니다.

확정→진행→완료

9. 안전장치

서버 재계산

confirm 이 클라이언트 계획을 쓰지 않고 다시 계산 → 변조된 비용·일정 방지.

마스터 버전 검사

시뮬레이션 후 마스터가 바뀌면 409. 오래된 화면으로 확정하는 것을 막는다.

낙관적 락

Order.@Version + 화면이 가진 version 비교. 동시에 다른 사용자가 상태를 바꾸면 409.

일괄 검증

마스터 폼은 오류를 모두 모아서 한 번에 보여주고, 하나라도 있으면 저장하지 않는다.

11. 읽다가 눈에 띈 점

취소하면 주문이 삭제된다. changeStatus 는 상태를 CANCELED 로 바꾼 뒤 orders.delete(order) 를 호출한다. 코드상으로는 목록의 "취소" 필터에 주문이 남지 않고 이력 행만 남는다. 의도라면 괜찮지만 CANCELED 상태·필터가 있는 것과 어긋나 보이고, 이 경로를 검증하는 테스트도 없다. 확인 필요.
로그인이 단일 하드코딩 계정이다 (AppController.ACCOUNT). 학습·데모용이 아니라면 교체 대상.
탐색이 완전 열거라 입력 규모에 민감하다 (6장 참고).

위 세 가지는 코드를 읽으며 본 것이고, 실행해서 재현한 것은 아니다.
