# PRD: 배터리 운송 주문·경로 시뮬레이션

### 이 문서에서 쓰는 말

| 말 | 뜻 |
|---|---|
| **1K** | 배터리 셀 1,000개. 모든 수량은 이 단위로 다룹니다. (예: 3,000K = 300만 개) |
| **기준 정보** | 계산의 바탕이 되는 값. 공장별 생산 능력·보관 한도·셀 1개 원가, 나라 사이 뱃길 일수, 배의 수와 하루 운항비 |
| **계획안** | 어떤 배가 언제 출발해 어느 나라를 어떤 순서로 돌고, 총 며칠에 얼마가 드는지를 정리한 운송 계획 |
| **확정** | 마음에 드는 계획안을 골라 정식 주문으로 만드는 것 |
| **금액 단위** | 시스템 안에서는 원 단위로 계산·저장하고, 화면에서는 억 원(소수 둘째 자리)으로 표시합니다 |

---

## 1. 배경

- **현재 문제**:
  - 한국 본사는 중국·일본·베트남·인도네시아 4개 공장에서 배터리 셀을 배로 들여옵니다.
  - 공장마다 하루에 만들 수 있는 양, 쌓아 둘 수 있는 양, 셀 한 개 값이 다르고, 나라 사이 뱃길 일수도 다릅니다.
  - 그래서 같은 물량이라도 **어떤 배가 어느 나라를 어떤 순서로 몇 번 도느냐**에 따라 걸리는 날짜와 비용이 크게 달라집니다. 게다가 "싸게"와 "빨리"는 서로 부딪칩니다.
- **관련 문서/이슈**:
  - `docs/INTENT.md` (설계 의도)

## 2. 목표

- **사용자가 무엇을 할 수 있어야 하는가**:
  1. 나라별로 필요한 수량을 입력하면, **걸리는 날짜와 비용을 함께 보여 주는 계획안 3가지**를 바로 비교할 수 있다.
  2. 마음에 드는 계획안을 골라 **주문으로 확정**할 수 있다. 확정한 주문은 그때 보았던 내용 그대로 나중에도 다시 볼 수 있다.
  3. 확정한 주문이 **지금 어느 단계인지** 관리하고, 누가 언제 바꿨는지 확인할 수 있다.
  4. 공장·뱃길·배에 관한 **기준 정보를 화면에서 직접** 고칠 수 있다.
- **비즈니스 또는 운영상 기대 효과**:
  - 확정한 주문과 변경 기록이 남아, 나중에 확정 당시의 내용과 변경 이력을 확인할 수 있다.

## 3. 대상 사용자

- **주요 사용자**: 로그인해서 주문을 입력·확정하고 진행 단계를 바꾸는 사람
- **보조 사용자**: 기준 정보(공장·뱃길·배)를 고치는 사람
- **관리자 또는 운영자 영향**:
  - 기준 정보를 고치면 **그 이후에 새로 하는 계산부터** 반영됩니다. 이미 확정한 주문은 바뀌지 않습니다.
  - **현재는 사용자 역할을 구분하지 않습니다.** 로그인한 사람은 누구나 주문도 하고 기준 정보도 고칠 수 있습니다. 로그인 계정도 하나뿐입니다.

## 4. 범위

이번 작업에 포함 (현재 시스템에 있는 기능을 요구사항으로 정리):

- [x] 나라별 수량 입력과 **계획안 3가지** 비교 (비용·날짜·배별 일정)
- [x] 계획안 **확정**, 확정 당시 내용 보존, 확정 후 **진행 단계 관리**와 변경 기록
- [x] 공장·뱃길·배에 관한 **기준 정보 수정**
- [x] **로그인**한 사람만 사용, 처리한 사람 기록

이번 작업에 포함하지 않음 (현재 없는 것이며, 필요 여부는 팀 결정):

- [ ] 공장 5곳 이상으로 **확장**하거나 새 나라를 화면에서 추가하는 기능
- [ ] 실제 배 위치·운송 실적 연동, 지연 시 계획 다시 짜기
- [ ] 알림(메일·메신저), 승인 절차, 보고서·통계, 외부 시스템(ERP 등) 연동
- [ ] 확정한 주문의 **수량 수정** (바꾸려면 취소 후 다시 주문)
- [ ] 기준 정보를 **누가 언제 바꿨는지**의 기록
- [ ] 취소된 주문을 다시 조회하는 화면

## 5. 사용자 흐름

**흐름 A. 계획안을 비교하고 주문을 확정한다**

1. 사용자가 로그인한 뒤 "주문 추가"에서 **나라별 필요 수량**을 입력합니다.
2. 사용자가 "시뮬레이션"을 누르면, 시스템은 **계획안 3가지**(운항비 최소 / 가장 빠르게 / 가까운 곳부터)를 계산해 보여 줍니다. 각 안마다 걸리는 날짜, 생산비, 운항비, 총비용, 배별 일정이 나옵니다.
3. 사용자는 계획 내용을 확인하고, 하나를 골라 메모를 적은 뒤 **확정**을 누릅니다.
4. 시스템은 **같은 수량으로 한 번 더 계산해서** 확인한 뒤 주문으로 저장합니다. 사용자는 새 주문 번호와 "확정" 상태를 확인합니다.
   - 계획안을 보는 사이 기준 정보가 바뀌었다면 확정되지 않고, "다시 시뮬레이션해 주세요"라는 안내가 나옵니다.

**흐름 B. 주문의 진행 단계를 바꾼다**

1. 사용자가 주문 목록에서 주문을 열어 상세 화면으로 갑니다.
2. 사용자가 "진행", "완료", "취소" 중 가능한 버튼을 누릅니다.
3. 시스템은 단계가 허용되는지 확인한 뒤 바꾸고, **누가 언제 무엇에서 무엇으로 바꿨는지** 기록합니다. 그 사이 다른 사람이 먼저 바꿨다면 반영하지 않고 "화면을 새로 고친 뒤 다시 시도해 주세요"라고 안내합니다.

**흐름 C. 기준 정보를 고친다**

1. 사용자가 "마스터 데이터"(기준 정보) 화면에서 값을 고치고 저장합니다.
2. 시스템은 모든 값을 검사합니다. 하나라도 틀렸으면 **아무것도 저장하지 않고** 틀린 항목을 전부 알려 줍니다.
3. 모두 맞으면 저장되고, 이후 새로 하는 계산부터 반영됩니다.

## 6. 기능 요구사항

**A. 계획안 계산과 비교**

- **FR-1**: 나라별(중국·일본·베트남·인도네시아) 필요 수량을 1K 단위로 입력하면, 확정 전에 몇 번이든 다시 계산해 볼 수 있다.
- **FR-2**: 서로 다른 기준의 **계획안 3가지**를 항상 함께 보여 준다.
  - **운항비 최소**: 배 운항 비용이 가장 적은 안
  - **가장 빠르게**: 한국에 가장 일찍 도착하는 안
  - **가까운 곳부터**: 한국에서 가까운 나라부터 처리하는 단순한 안
- **FR-3**: 각 계획안마다 총 걸리는 날짜, 생산비, 운항비, 총비용, 배별 일정(언제 출발해 어느 나라에서 얼마를 싣고 언제 돌아오는지)을 보여 준다.
- **FR-4**: 계획은 다음 **업무 규칙**을 따른다.
  - **생산**: 모든 공장은 주문한 날(0일째)에 동시에 생산을 시작한다. 하루 생산량은 "공장의 하루 최대치", "남은 보관 공간", "남은 주문량" 중 가장 작은 값이다.
  - **보관 한도**: 공장 창고가 가득 차면 배가 실어 가기 전까지 생산이 멈춘다.
  - **수거**: 배는 도착한 시점에 그 공장에 쌓인 물량을 **전부** 싣는다. 한 나라는 **한 척의 배만** 방문한다.
  - **나눠서 수거**: 주문량이 보관 한도보다 많으면 여러 번에 나눠 가져온다. 방문 횟수는 "주문량 ÷ 보관 한도"를 올림한 값이다. 나눠 가져올 때는 한국에 들러 내려놓고 다시 출항한다.
  - **출발 시점**: 배는 공장 창고가 찰 때까지 기다리지 않도록 **가능한 한 늦게 출발**한다. 한국에서 기다리는 시간은 비용이 들지 않는다.
  - **소요 일수**: 가장 늦게 한국에 돌아오는 배를 기준으로 센다.
  - **배 수**: 설정된 배 척수를 넘겨 쓰지 않는다.
- **FR-5**: **비용 = 생산비 + 운항비**. 생산비는 "수량 × 셀 1개 원가", 운항비는 "배가 바다에서 보낸 총 일수 × 배 한 척의 하루 운항비"다.
- **FR-6**: 입력이 허용 범위를 벗어나면(수량이 음수이거나 총 수량이 0이거나 허용 한도를 넘으면) 이유를 그대로 알려 준다.
- **FR-7**: 시스템은 계산 결과를 하루씩 다시 따라가며 스스로 검산한다. 싣는 양과 창고 재고가 맞지 않으면 그 계획안을 내놓지 않는다.

**B. 주문 확정과 보존**

- **FR-8**: 계획안 하나를 골라 메모(선택)와 함께 **주문으로 확정**한다.
- **FR-9**: 확정할 때 시스템은 화면에 표시된 값을 믿지 않고 **같은 수량으로 직접 다시 계산**한 결과만 저장한다.
- **FR-10**: 계획안을 본 뒤 기준 정보가 바뀌었다면 **확정을 막고** 다시 계산하도록 안내한다.
- **FR-11**: 확정한 주문은 **확정 당시의 계획과 기준 정보를 그대로 보존**한다. 이후 원가·뱃길·배 사정이 바뀌어도 과거 주문의 날짜와 금액은 변하지 않는다.

**C. 주문 조회와 진행 관리**

- **FR-12**: 주문 목록을 상태별로 볼 수 있고, 주문 상세에서 변경 기록과 확정 당시의 계획 전체를 다시 볼 수 있다.
- **FR-13**: 주문 상태는 정해진 순서로만 바뀐다.

  | 지금 상태 | 바꿀 수 있는 상태 |
  |---|---|
  | 확정 | 진행, 취소 |
  | 진행 | 완료, 취소 |
  | 완료 | 없음 (끝) |
  | 취소 | 없음 (끝) |

- **FR-14**: 모든 상태 변경은 **이전 상태, 새 상태, 처리한 사람, 일시**가 기록된다.
- **FR-15**: 두 사람이 동시에 같은 주문을 바꾸려 하면 **먼저 처리된 한 건만 반영**하고, 나머지 사람에게는 새로 고침 후 다시 시도하도록 안내한다.
- **FR-16**: 주문을 **취소**하면 주문은 목록에서 사라지고 변경 기록만 남는다. (이 동작이 의도한 것인지는 확인이 필요합니다. → 열린 질문 Q2)

**D. 기준 정보 관리**

- **FR-17**: 다음 값을 화면에서 직접 고칠 수 있다.
  - 공장별: 하루 최대 생산량, 보관 한도, 셀 1개 원가
  - 나라 사이 뱃길 일수
  - 배의 수, 배 한 척의 하루 운항비
- **FR-18**: 값이 허용 범위를 벗어나면 저장하지 않는다. 틀린 항목을 **한꺼번에 모두** 알려 주고, 입력했던 값은 화면에 남겨 둔다. (구체적인 허용 범위 숫자는 INTENT.md의 "조정될 수 있는 값" 참조)
- **FR-19**: 처음 시작할 때 기준 정보가 비어 있으면 기본값을 채운다. 이미 값이 있으면 덮어쓰지 않는다.

**E. 접근**

- **FR-20**: 로그인하지 않으면 로그인 화면 외에는 아무것도 볼 수 없다.
- **FR-21**: 주문과 상태 변경에는 **처리한 사용자의 아이디**가 기록된다.

## 7. 비기능 요구사항

- **성능**:
  - 시스템은 모든 경우의 수를 따져 가장 좋은 안을 고르는 방식이라, **공장 4곳, 배 4척 이하**일 때를 전제로 합니다. 공장이나 배를 늘리면 계산이 급격히 느려질 수 있습니다.
- **접근성**:
  - 정해진 요구사항이 없습니다.
- **보안**:
  - 로그인한 사람만 사용할 수 있습니다.
  - 확정은 화면 값이 아니라 시스템이 다시 계산한 결과로만 합니다. 화면 값을 조작해도 잘못된 금액이 저장되지 않습니다.
  - **주의**: 계정이 하나뿐이고 아이디와 비밀번호가 모두 `admin`으로 정해져 있습니다. 실제 운영에 쓰기에는 안전하지 않은 상태입니다.
- **로깅/모니터링**:
  - 주문 상태 변경 기록(누가·언제·무엇에서 무엇으로)은 있습니다.
  - 기준 정보 변경 기록, 시스템 오류 알림, 사용 현황 모니터링은 요구사항으로 정해져 있지 않고 현재 없습니다.

## 8. 수용 기준

- [ ] Given 한 나라의 주문량이 그 공장의 보관 한도보다 많을 때, When 계획안을 계산하면, Then 그 나라는 "주문량 ÷ 보관 한도"를 올림한 횟수만큼 나눠 방문하고, 나눠 싣는 양의 합이 주문량과 같다.
- [ ] Given 기본 기준 정보(INTENT.md "조정될 수 있는 값" 참조)에서 12,000K를 네 나라에 3,000K씩 주문할 때, When 계획안을 계산하면, Then 방문 횟수는 중국 1회·일본 2회·베트남 1회·인도네시아 1회이고 생산비 합계는 78억 원이다. (생산비는 어느 계획안이든 같다)
- [ ] Given 한 나라의 물량이 모이는 데 시간이 걸릴 때, When 계획안을 계산하면, Then 배는 물량이 모이는 날에 맞춰 늦게 출발하고, 한국에서 기다린 시간은 운항비에 포함되지 않는다.
- [ ] Given 모든 나라의 주문 합이 0일 때, When 시뮬레이션을 누르면, Then 이유를 보여 주고 계산하지 않는다.
- [ ] Given 계획안 3가지가 나왔을 때, When "운항비 최소"와 "가장 빠르게"를 비교하면, Then 운항비 최소 안의 운항비는 가장 빠르게 안보다 많지 않고, 가장 빠르게 안의 소요 일수는 운항비 최소 안보다 길지 않다. ("가까운 곳부터" 안과의 대소 관계는 보장하지 않는다)
- [ ] Given 시뮬레이션 뒤에 누군가 기준 정보를 바꿨을 때, When 확정을 누르면, Then 확정되지 않고 다시 시뮬레이션하라는 안내가 나온다.
- [ ] Given 주문을 확정한 뒤 원가나 뱃길을 바꿨을 때, When 그 주문 상세를 열면, Then 확정 당시의 날짜와 금액이 그대로 보인다.
- [ ] Given 확정 상태의 주문일 때, When 완료로 바꾸려 하면, Then 허용되지 않는다. (확정 → 진행 → 완료 순서만 가능)
- [ ] Given 같은 주문을 두 사람이 열어 둔 상태에서, When 한 사람이 먼저 상태를 바꾼 뒤 다른 사람이 바꾸려 하면, Then 뒤의 요청은 반영되지 않고 새로 고침 안내가 나온다.
- [ ] Given 기준 정보에 허용 범위를 벗어난 값이 여러 개 있을 때, When 저장하면, Then 기존 값은 그대로 유지되고 틀린 항목이 모두 표시된다.
- [ ] Given 로그인하지 않았을 때, When 어떤 화면 주소로 들어가면, Then 로그인 화면으로 이동한다.
- [ ] Given 잘못된 아이디 또는 비밀번호를 입력했을 때, When 로그인하면, Then 로그인되지 않고 올바르지 않다는 안내가 나온다.

## 9. 검증 계획

- **단위 테스트** (계산 규칙을 자동으로 확인하는 테스트가 있습니다):
  - 방문 횟수 계산, 싣는 양의 합이 주문량과 같은지, 한 나라는 한 척만 방문하는지
  - 생산비 계산, 배의 출발 시점, 나눠 수거, 보관 한도에서 생산이 멈추는지
  - 운항비 최소 안과 가장 빠른 안의 관계(기본 입력 한 가지로만 확인), 배 척수 상한, 빈 주문 거부
- **통합 테스트** (실제 화면 흐름에 가깝게 확인하는 테스트가 있습니다):
  - 로그인 필요 여부, 잘못된 비밀번호, 3가지 안 계산, 빈 주문 거부
  - 확정 → 진행 → 완료와 변경 기록, 기준 정보가 바뀐 뒤 확정 거부
  - 기준 정보 수정 시 이전 주문 보존, 잘못된 기준 정보는 저장 안 됨
  - 완료된 주문을 취소하려 하면 거부되는 것은 테스트가 있습니다.
  - **빠진 부분**: 주문 **취소가 성공하는 경로**, 화면 안의 동작, 그리고 운항비 최소·가장 빠른 안의 관계를 **다양한 입력으로** 확인하는 테스트(현재는 기본 입력 한 가지뿐)
- **수동 확인**:
  - 앱을 실행해서 다음을 직접 확인합니다: 3가지 안 비교 화면, 확정 → 진행 → 완료, **취소 직후 화면**, 기준 정보 저장 오류 표시, 두 브라우저로 동시에 상태 바꾸기

## 10. 리스크와 열린 질문

- **리스크**:
  - **권한 없음**: 로그인한 누구나 기준 정보를 바꿀 수 있고, 계정은 공용 하나입니다. 잘못 고친 기준 정보가 이후 모든 계산에 영향을 줍니다. (과거 주문은 보호됨)
  - **기준 정보 변경 기록 없음**: 누가 언제 어떤 값을 바꿨는지 알 수 없습니다.
  - **취소 시 주문이 삭제됨**: 취소한 주문은 목록에서 사라져 나중에 조회하거나 집계할 수 없습니다.
  - **계산 규모 한계**: 공장이나 배를 늘리면 계산이 급격히 느려질 수 있습니다.
  - **기준 정보 동시 저장**: 기준 정보 저장에도 동시 수정 방지가 걸려 있어, 두 사람이 동시에 저장하면 한쪽이 오류가 날 수 있습니다. 이때 사용자에게 어떻게 안내할지는 정해져 있지 않습니다. (코드 확인, 실행은 미확인)
- **결함 후보** (현재 동작이 "잘못되면 이유를 그대로 알려 준다"(FR-6 등)와 어긋나 보이는 것. 팀이 확인해 수정 여부를 정해야 합니다):
  - **존재하지 않는 주문 조회 시 서버 오류**: 없는 주문 번호로 상세 화면을 열면 안내 없이 서버 오류(HTTP 500)가 납니다. (리뷰 과정에서 실행 중인 서버로 확인)
  - **취소 직후 같은 오류가 날 가능성이 매우 높음**: 취소는 주문을 삭제한 뒤 그 주문의 상세 화면으로 이동하므로 위와 같은 상황이 됩니다. (취소 자체는 실행해 보지 않음)
  - **계산 검산 실패 시 일반 서버 오류**: 시스템이 스스로 검산해서 틀린 것을 발견하면, 이유를 설명하는 안내 없이 일반 서버 오류로 끝납니다. (코드 확인: 업무 오류만 안내로 바꿔 주고 이 경우는 처리하지 않음)
- **열린 질문** (설계 의도에 관한 질문은 INTENT.md에 있습니다):
  - **Q1.** 이 도구를 **실제로 누가, 어떤 업무**에 쓰는가? (코드와 문서에 없음)
  - **Q2.** **취소하면 주문이 사라지는 것**이 의도한 동작인가? 취소 주문도 조회해야 하는가? (취소 직후 화면 오류는 위 "결함 후보" 참조)
  - **Q3.** 사용자별로 **권한을 나눠야** 하는가? (예: 기준 정보는 일부만 수정 가능) 사용자별 계정이 필요한가?
  - **Q4.** **기준 정보 변경 기록**(누가 언제 무엇을 바꿨는지)이 필요한가?
