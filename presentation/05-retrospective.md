# 5. 회고

Loop를 직접 설계하고 구현하며, 코드와 Diff 요약, Report 등의 Evidence를 리뷰하는 방식으로 팀 프로젝트를 진행했습니다.

이번 팀 프로젝트를 진행하면서 느꼈던 점을 팀원별로 적어 주세요.

| 팀원 이름 | 좋았던 점 | 아쉬웠던 점 |
|---|---|---|
| 김현곤 | AI 정말 많은 일을 할 수 있다는 사실에 매일같이 놀라웠습니다. 개인적으로는 외부에서 프로젝트 실행을 하고 있는데 현장에서는 아직 AI와 동떨어진 업무를 수행중이라서 많이 안타까운 마음이고 가능하면 AI를 적극 도입하도록 힘써야겠다는 다짐을 하게 되었습니다. | AI를 통해서 많은 산출물이 쌓이는데, 생성되는 자료의 볼륨이 생각보다 많아지는것 같아서 이에 실질적인 리뷰방법에 대한 고민이 많이 필요할 것 같습니다. |
| 문형석 | **1. Action과 Gate를 모두 맡아 보며 "구현자가 놓치는 것"을 직접 경험했습니다.** 내 필요 납기일 PR(#23)에서는 리뷰어가 서버 검증 누락(5.5가 5로 저장됨)을 찾아냈고, 반대로 공장 운영비 PR(#25)을 리뷰할 때는 기본값에서 "비용 최소"와 "가장 빠르게"가 같은 안이 되어 선택식을 검증하지 못하는 테스트의 빈틈을 숫자로 짚어 작성자가 반영했습니다. 한쪽만 했다면 알기 어려운 관점이었습니다.<br>**2. AI의 "확인했다"를 근거로 바꾸는 습관을 익혔습니다.** 테스트를 직접 실행해 수치를 보고하고, 새 테스트를 기능이 없는 옛 코드에서 돌려 실패하는지 확인하고(JUnit 4개·E2E 6개 실패), 보고서에 "확인하지 못한 것"을 반드시 적는 방식입니다. 리뷰어도 그 증거를 보고 빠르게 판단할 수 있었습니다.<br>**3. 문서가 AI와 협업하는 기준이 된다는 것을 체감했습니다.** PRD·INTENT의 6원칙이 코드 리뷰의 판단 기준이 되었고, 이를 바탕으로 영역(Green/Yellow/Red)에 맞춰 증거를 보는 깊이를 달리했습니다. 이 경험으로 현장 과제에서도 쓸 수 있도록 AGENTS.md와 작업 방식 문서를 1인 프로젝트용으로 정리해 둘 수 있었습니다.<br>**4. 짧은 기간에 개발 흐름 전체를 경험했습니다.** 코드 이해 → PRD/INTENT → E2E·단위·성능 테스트 → Loop 설계 → PR 리뷰 → 기능 추가까지 이어서 해 보면서, 각 단계에서 AI에게 무엇을 맡기고 사람이 무엇을 확인해야 하는지 구분할 수 있었습니다. | **1. '인지부채'를 직접 겪었습니다.** 내 precheck에 "소수는 서버가 검증"이라고 적었지만 실제로는 확인하지 않은 내용이었고, 리뷰어가 재현해서 알려 주었습니다. AI가 쓴 문장이 그럴듯하다는 이유로 넘어가면 내가 모르는 코드와 문서가 쌓인다는 것을 실감했고, 그래서 코드 리뷰와 "직접 확인"이 더 중요하다고 느꼈습니다.<br>**2. 직접 설계한 Loop를 끝까지 돌려 보지 못했습니다.** `/refactoring`의 첫 실행이 대상이 불분명한 `main` 브랜치라 사람에게 넘기는 단계(HITL)에서 종료되어 implement·verify까지의 실제 동작은 확인하지 못했고, 필요 납기일은 같은 구조를 수동으로 따라 진행했습니다.<br>**3. 여러 PR이 같은 파일을 바꿔 병합 조율에 시간이 들었습니다.** 회원 가입, 필요 납기일, 고객사 이름, 공장 운영비가 `Order`·`OrderDetail`·주문 목록 화면을 함께 바꿔서 병합 때마다 충돌을 풀고 전체 테스트를 다시 돌려야 했습니다. 목록 열 개수나 `colspan`처럼 git이 잡지 못하는 의미상 충돌은 테스트가 알려 줘서야 알았고, 머지 순서를 미리 조율하지 못한 점이 아쉽습니다.<br>**4. 내가 만든 테스트 도우미의 약점을 뒤늦게 알았습니다.** E2E의 목록 건수 도우미가 화면이 JS로 바뀐 뒤 간헐적으로 실패했고(36회 중 2회), 같은 포트를 쓰는 Playwright를 겹쳐 돌려 12건이 실패한 일도 있었습니다. 테스트의 안정성과 실행 환경까지 미리 점검하지 못했고, 시간이 짧아 반복 실행으로 확인하는 데 한계가 있었습니다. |
| 오재석 | 개발할 때 막연하게 시키기만 했던 AI를 어떻게 하면 더 효율적이고 좋은 퍼포먼스로 활용할 수 있는지에 대해 공부해 볼 수 있었고, 활용 방향에 대해서도 고민해 볼 수 있어 좋았습니다. Loop 엔지니어링으로 AI와 인간의 역할을 명확히 구분하면서도, 견고한 시스템을 단기간에 구축할 수 있어, 현업에서도 이러한 부분을 잘 활용해야겠다는 생각을 했습니다. | 단기간에 진행한 만큼 프로젝트에 직접 개입하여 명확하게 AI와의 역할을 구분하는 과정이 쉽지 않았던 것 같습니다. 과정 중에 강사님께서 꾸준히 말씀하신 '인지부채'를 실감하기도 한 부분입니다. 좋은 코드 또한 AI를 통한 리팩토링으로 AI에 의존하게 되다 보니, '인지부채'를 겪지 않기 위해서는 반드시 코드 리뷰 과정이 중요하다는 것을 실감할 수 있었습니다. |
| 우주상 | 실무에서도 AI를 활용하고 있어서, 교육에서 배운 내용을 바로 적용할 수 있었습니다. 그래서 저에게 얻는 것이 많은 교육이었습니다. 또한 배운 내용이 하나씩 쌓여 최종 결과물로 이어지는 구성이라, 각 내용을 쉽게 이해하고 익힐 수 있었습니다. | 특별히 아쉬웠던 점은 없었습니다. |
