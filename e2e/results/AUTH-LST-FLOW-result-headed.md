## 관찰 사항

- **LST-04** 주문이 0건인 DB 에서만 확인할 수 있는 시나리오라, `data/` 를 지우고 앱을 새로 시작한 직후 가장 먼저 단독 실행했습니다. 목록에 '주문이 없습니다.' 가 표시되는 것을 확인했습니다. 파일 순서상 `auth.spec.ts` 의 AUTH-09 가 주문을 먼저 만들기 때문에, 전체를 한 번에 실행하면 이 시나리오는 건너뛰게 됩니다.
- **AUTH-03** 잘못된 비밀번호로 로그인하면 주소가 `/login` 이 아니라 `/login;jsessionid=...` 로 나왔습니다. 로그인 화면을 처음 열 때 세션이 만들어지고 쿠키가 아직 없어서 서버가 폼 주소 끝에 세션 번호를 붙이기 때문입니다. 동작에는 문제가 없지만 세션 번호가 주소에 노출되므로 팀에서 확인할 만한 항목입니다. 테스트는 이 형태를 허용하도록 작성했습니다.
- **AUTH-07 / AUTH-09** 비로그인 API 호출은 401(리다이렉트 아님)이고, 비로그인 상태의 상태 변경 요청은 302 로 `/login` 으로 이동했으며 주문 상태는 '확정' 그대로였습니다.
- **FLOW-02** 기준 정보를 바꿨다가 되돌린 뒤에도 이미 확정한 주문의 요약(총 수량·소요 일수·생산 원가·운항비·총 비용)이 같았습니다.

## 다시 실행하는 방법

LST-04 까지 확인하려면 주문이 0건인 DB 로 시작해야 합니다. 앱을 끄고 `data/` 를 지운 뒤 앱을 새로 시작합니다(기존 주문과 기준 정보가 모두 사라지므로 필요하면 먼저 백업).

```
cd e2e
npx playwright test tests/lst.spec.ts -g "LST-04" --headed
npx playwright test --grep-invert "LST-04" --headed
```

(주문이 이미 있는 DB 에서 그냥 `npx playwright test` 를 실행하면 LST-04 만 건너뛰고 나머지 16건은 같은 결과가 나옵니다.)

원본 데이터는 `e2e/results/LST-04-clean-db-headed-run.json`(LST-04)과 `e2e/results/AUTH-LST-FLOW-headed-run.json`(나머지 16건)입니다. 실행할 때마다 주문과 기준 정보 변경 번호가 DB 에 쌓입니다.
